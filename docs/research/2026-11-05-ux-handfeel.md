# Moss 使用手感（handfeel）调研与改进基线

日期：2026-11-05 · 触发：owner 追加要求「调研如何优化使用手感，将使用做的够好」
范围：交互面响应性、启动到可输入、首字延迟、技能/工具可见性、错误与提示的可操作性。
本文只记录**实测**与**可验收的改进项**；未实测的数字不写。

## 1. 当前实测基线

环境：macOS（本机），`npm run bench:tui-feel`（PTY + pyte，脚本化 provider，零配额）。

| 场景   | composer_ready | typing echo | draft echo | first stream | interrupt |
| ------ | -------------- | ----------- | ---------- | ------------ | --------- |
| 100x30 | 843 ms         | 50 ms       | 10 ms      | 263 ms       | 61 ms     |
| 70x24  | 737 ms         | 44 ms       | 6 ms       | 249 ms       | 88 ms     |

其他实测：

- `node dist/cli.js --version`：**0.28 s**（进程启动 + 配置解析 + 版本打印）
- `moss skill list`（1 个技能）：即时返回，输出含目录成本/使用次数/评测有无
- TUI 里 composer 出现后输入回显稳定在 **44–50 ms**，属于"跟手"
- 中断（Esc）到回显恢复 **61–88 ms**，可接受

结论：**可输入前 ~800 ms 是最大体感痛点**；输入后链路已经够快。

## 2. 参考产品的"手感"机制（来自本仓库 2026-11-04 调研清单）

出处在 `docs/research/2026-11-04-next-capabilities/claude-code.md` 与 `cursor.md`，这里只摘与手感直接相关的：

1. **预算式披露**：技能目录按 1% 上下文 / 8,000 字符封顶，条目 1,536 字符、最久未用优先压缩
   → 提示词稳定 + 启动可预测（Moss 已实现目录预算，缺"最久未用优先"排序与逐条 1,536 上限）。
2. **命令面可操作性**：`/context` 展示 token 分解；`/skills`、`/mcp`、`/plugins` 都能看到"成本/状态"，
   而不只是名字（Moss 本轮补上技能的目录成本/使用次数/评测可见性）。
3. **MCP 每个工具可 `alwaysLoad` / `defer`** + 描述长度上限，避免连接后一次性灌入（Moss 已实现）。
4. **spinner/状态行**：Claude Code 在等待时给出当前动作（工具名 + 目标），Moss TUI 已有工具行；
   但**启动阶段的"正在加载技能/MCP"没有可见文字**——用户只看到空屏等待，这是 800 ms 的体感放大器。
5. **压缩/上下文提示**：压缩前给理由与范围，压缩后可恢复（Moss 已有 compact 提示与 checkpoint）。

## 4. 本轮已落地（2026-11-05）

**D10 第一片：技能的成本 / 使用 / 评测可见性**（`moss skill list` + 本地计数器）

- 每行新增：`used`（真实加载次数，来自 `.moss/skills-usage.json`）、`catalog`（该技能完整目录条目
  的字符成本，直接用提示词同一个渲染器算出，不是估算）、`evals`（是否有 `evals/evals.json`）
- 汇总行给出：目录总字符 / 预算（默认 8,000）、当前策略（full / compact / mixed）、无预算上限时的字符数
- 计数器由 `skill` 工具在**真实加载成功后**写入，`-p` 真实运行验证：加载后 `moss skill list` 的 `used`
  从 0 → 1；文件落在 `.moss/skills-usage.json`（runtime artifact，已加入工作区 `.moss/.gitignore` 模板）

这条改进的价值：技能"占多少上下文"和"到底用不用"第一次同时可见，用户可以在扩大技能库前判断
哪条该压缩/删除，而不是等提示词变慢。

## 4.1 H2 已落地：分阶段启动计时（2026-11-05）

`MOSS_STARTUP_TIMING=1` 时启动打印一行 `[startup] timing: config=…ms agent=…ms skills=…ms
total=…ms`（stderr，`-p` 的 stdout 保持干净；默认关闭）。三个标记点是真实阶段：配置解析完成、
`MossAgent` 构造完成、技能目录/斜杠命名空间装载完成。真实一次 `-p --mock` 运行：

```
[startup] timing: config=222ms agent=302ms skills=584ms total=584ms
```

回归入口：verify stage `startup-timing`（4 条断言：有行、单调、默认关闭、`0` 也关闭）。
**H1 的下一步因此可量化**：composer 骨架只该覆盖 `skills=584ms` 之前的等待（≈0.6s 里 config+agent 已占
约 0.3s，先渲染 composer 的真实收益上限约 0.3–0.5s），并且改造后可以直接对比这一行。
