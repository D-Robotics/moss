# Moss v0.24 规划 · 诚实度收口 + 中文用户面（2026-10-02 立项）

v0.23 已发布（能力层可用性：mcp/device/skill 生命周期）。v0.24 主题从用户视角取证得出：**完成判定不再说谎，中国用户不再半屏英文**。本版不动引擎语义，机器人闭环（governing P0）验收链不变。

## 取证结论（2026-10-02，全部实证过）

1. `prod/ux-hardening` 分支上有两个已修但未合并的**用户信任级缺陷**（分支 2026-10-01 起，main 无冲突面，仅 `src/cli/approval.ts` 一处内容冲突）：
   - **F23 审批旁路**（`cffbeeca`）：子代理不带审批门——父进程 4 次被拒的写操作，委派给 full-scope 子代理后无门直接执行（证据：会话 `cli-20261001040552-0ba7f900`，hello.txt 在父级全部拒绝后写入）。
   - **F24 证据语义**（`cf3407d0`）：`exists` 比较器把 "missing" 判为存在（假 PASS 于验收门）；record_evidence 无条件覆盖显式裁决（违反自身文档承诺）。
2. **i18n 断层**：brief help / onboarding / /usage / provider 错误面已双语（`cli-locale.ts` 模式，`ca3d6095`/`54f9f7d5`），但 v0.23 三条新命令线（device/mcp/skill，约 400+ 用户可见行）与 task 状态面全英文——`rg 'zh ?' device-commands.ts mcp-commands.ts skill-commands.ts task-run.ts` 零命中；zh locale 下实跑 `moss device`/`mcp`/`skill` 确认半屏英文。CLI 83 文件仅 9 个有 zh 能力。
3. 用户首要身份是 RDK（中文）机器人开发者，公司入口即 `developer.d-robotics.cc`。中文面是用户视角的一等问题，不是润色。

## 总目标

一句话：**中文 RDK 开发者用母语跑完 moss 设备闭环的每一步；审批与证据机制对父/子代理同样诚实。**

## 量化验收（基线 → 目标）

| 指标                               | v0.23                 | v0.24 目标                                               |
| ---------------------------------- | --------------------- | -------------------------------------------------------- |
| 审批门覆盖                         | 子代理无门（F23）     | 子代理继承父门，spec 红绿证明                            |
| exists 假 PASS                     | "missing"→PASS（F24） | 负向词表判 FAIL，显式裁决不再被覆盖，spec 锁定           |
| zh 下 `moss device/mcp/skill/task` | 全英文                | 全部用户可见字符串 zh/en 双形态（实体名/命令输出不翻译） |
| CLI zh 覆盖文件数                  | 9/83                  | +4（device/mcp/skill/task-run）                          |

## 批次（每批独立 verify + CI 绿后合 main）

- **W1 · 合并 prod/ux-hardening（F23+F24）**——沉没成本对称出局：分支上已完成+带 spec 的工作，合并成本 < 重写成本，方向与用户信任目标一致。
  - 唯一冲突 `approval.ts`：main 的 A6.52/53（信任选项分级标签）与 F23 的拒绝文案（告知委派也会被拒）**都保留**——两者改的是同区不同语句，语义正交。
  - 验收：merge 后 `npm run verify` 全绿（含新增 `subagent-approval-inheritance.spec.mjs`、`evidence-model.spec.mjs` 实跑）。
- **W2 · device 命令双语**：`src/cli/device-commands.ts` 按 `help.ts` 模式（`isZhLocale()` + zh 分支）双语化；错误路径（test 失败的下一步指引）必须有 zh 变体。验收：spec 断言 zh/en 两形态 + `LANG=zh_CN.UTF-8 moss device list/test` 实跑取证。
- **W3 · mcp/skill/task 命令双语**：同模式落 `mcp-commands.ts`、`skill-commands.ts`、`task-run.ts`（状态表字段标签 TASK/GOAL/PHASE/VERDICT 给 zh 变体；值与命令输出不翻译）。验收同 W2。
- **W4 · 收尾与发布**：全量 verify + smoke；PTY dogfood 用 zh 会话实走 device/mcp/skill 命令；版本 0.24.0；发布口径按 `docs/release-policy.md`。

## Non-goals

- 不引入 i18n 框架/目录结构（`zh ?` 三元分支是既定模式，规模未到换框架的临界点）。
- 不翻译模型回答、代码、标识符、工具原始输出（`buildAnswerLanguageLayer` 已负责回答语言）。
- 不做 TUI 内嵌文案的大规模双语化（本版只到命令输出层；TUI 面若有高频英文行，逐行评估后入 v0.25）。
- 不改 Task OS 引擎/verdict 语义（F24 只修比较器语义与覆盖行为，验收链结构不变）。
- 不做 fleet 多设备调度（`--device`→运行时解析留待 v0.25，本版 `target_device` 仍为元数据）。

## 边界与风险

- **风险 1**：合并 F23 需确认 main 上 4d500327（trust 持久化）与 F23（子代理继承门）正交——信任持久化只放宽父会话交互审批，子代理继承的是"门"本身不是"已信任名单"。合并后跑 `subagent-approval-inheritance.spec.mjs` 验证。
- **风险 2**：zh 分支字符串无编译期检查，靠 spec 锁定关键形态；spec 必须覆盖每命令至少 1 条 zh 断言 + 1 条 en 断言。
- **风险 3**：`moss task` 无任务时的空态输出也在双语范围，勿漏。

## 验证方式（写死）

1. 每批：`npm run verify`（format:check+lint+typecheck+193 spec+smoke）全绿。
2. W2/W3 每命令：`LANG=zh_CN.UTF-8 node dist/cli.js <cmd>` 与 en 形态各实跑一次，输出贴进 commit message 或 PR 描述。
3. W1：两个新 spec 文件必须出现在跑测清单且实跑通过（不是仅存在）。
4. W4：PTY 会话（zh locale）真实走 device/mcp/skill 三命令，截图/输出入 tag 证据。
