# MOSS Jev 120 题评测集规范

状态为评审草案。配额、评分规则和验收协议用于指导采题与复核。文中的样例用于说明题型，正式入库仍需通过来源与验收审查。

## 1. 评测目标与数量

评测回答三个问题。Jev 是否增加了经过独立验收的真实修复？证据分散、日志过长或验证过期时，Jev 是否改善了执行？这些改善对应多少模型用量、耗时和工具调用？

评测集包含 **120 个独立题目**。其中 **96 题从未修复的代码快照开始**，包括 72 道普通真实修复和 24 道带长日志的真实修复。其余 24 题从可复现的运行状态开始，检查 MOSS 如何处理收尾、过期证据和容易引发误拦的情况。完整修复题用于计算修复通过率，机制与对照题各用独立的通过标准。

| 主类型             | L1 基础 | L2 中等 | L3 困难 | L4 高难 |    合计 |
| ------------------ | ------: | ------: | ------: | ------: | ------: |
| 真实代码修复       |      14 |      22 |      22 |      14 |  **72** |
| 带长日志的真实修复 |       2 |       6 |       8 |       8 |  **24** |
| 收尾与过期证据     |       4 |       6 |       4 |       2 |  **16** |
| 误拦与开销对照     |       4 |       2 |       2 |       0 |   **8** |
| **合计**           |  **24** |  **36** |  **36** |  **24** | **120** |

完整修复题只计入一个主类型，可附多个标签，例如「跨模块」「缓存」「隐藏边界」「测试并发」。同一上游缺陷产生的日志切片、提示改写和复跑记录使用同一个修复题 ID。引用该缺陷的机制检查点另有 ID，保留相同的来源分组。

### 校准组与正式组

24 题用于校准评分器、日志分块和 Jev 阈值，96 题用于正式对照。按主类型和难度抽取，正式组分母在开跑前冻结。

| 主类型             | 校准组 L1/L2/L3/L4 | 正式组 L1/L2/L3/L4    | 正式组总数 |
| ------------------ | ------------------ | --------------------- | ---------: |
| 真实代码修复       | 3 / 4 / 4 / 3      | 11 / 18 / 18 / 11     |         58 |
| 带长日志的真实修复 | 0 / 1 / 2 / 2      | 2 / 5 / 6 / 6         |         19 |
| 收尾与过期证据     | 1 / 1 / 1 / 0      | 3 / 5 / 3 / 2         |         13 |
| 误拦与开销对照     | 1 / 0 / 1 / 0      | 3 / 2 / 1 / 0         |          6 |
| **合计**           | **5 / 6 / 8 / 5**  | **19 / 30 / 28 / 19** |     **96** |

正式组有 77 道完整修复题和 19 道机制题。同一缺陷、同一隐藏验收或同一运行记录的派生题按来源一起划入同一组。优先留出完整项目，观察 Jev 在校准阶段未覆盖的项目上的表现。临近版本中发生在同一模块、能用相同补丁解决的故障在切分前查重。

## 2. 四档难度评分

每题由两位评审独立打分。评分依据是给 Agent 的材料、参考修复需要解决的问题、证据依赖和验证范围。每项 0–3 分，总分 0–12 分。

| 维度         | 0 分                               | 1 分                                         | 2 分                                                       | 3 分                                                                   |
| ------------ | ---------------------------------- | -------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| **定位难度** | 复现直接指出唯一错误位置           | 沿一条调用链查找根因，通常在一个模块内确认   | 至少两个合理假设，需要用代码或复现排除其一                 | 多个缺陷独立存在或相互遮蔽，需要分步隔离和对比不同条件下的结果         |
| **改动耦合** | 一个局部行为，调用方无需调整       | 一个主要模块，需保留接口、数据形状或边界行为 | 多个相互依赖的模块，需兼顾兼容、迁移或共享契约             | 多条路径相互影响，需同时维护行为、性能或状态一致性等多个约束           |
| **证据负担** | 单一短输出，证据直接可见           | 需对照输出与代码，或在单段日志定位一条线索   | 关键证据分散在不同区段、文件或工具结果，含无关但可信的错误 | 需关联多个来源、运行阶段或代码版本，缺少其中一项会导向错误修复         |
| **验证难度** | 一个稳定的直接回归检查即可证明交付 | 需要公开用例和同一契约的边界检查             | 需要相互独立的检查，或公开检查通过仍可漏掉严重回归         | 需要多轮或跨条件验证，例如后续写入使多项检查失效，或性能结果需重复测量 |

| 总分 | 档位        | 典型交付                                         |
| ---- | ----------- | ------------------------------------------------ |
| 0–2  | **L1 基础** | 修复已定位的边界条件并通过单一回归               |
| 3–5  | **L2 中等** | 从症状定位模块，修复后验证边界与兼容行为         |
| 6–8  | **L3 困难** | 排除多个假设，处理跨模块契约或公开验证覆盖不足   |
| 9–12 | **L4 高难** | 联合解决相互影响的约束，并用多轮独立验证证明结果 |

每个分数至少记录一条可指认的依据。两位评审分到不同档位，或某维度相差 2 分以上，由第三人复核并说明最终分值。分值在正式 A/B 前冻结，某个模型跑得快慢只用于复盘评分。日志字数、文件数量和补丁行数作为题目属性记录。长而重复的日志可以是低难度题，短而分散的证据也可以是高难度题。

收尾和对照题按 Agent 在检查点需要处理的问题评分。例如单次改动后缺一项明确测试，验证难度较低。两项并行检查跨越不同范围的写入，验证和证据负担均提高。

## 3. 题目来源与入库记录

| 数量与用途              | 来源                                                       | 每题必须保存的来源证据                                                              |
| ----------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **72 道真实修复**       | 已解决的开源 issue 和对应 PR，或授权使用的内部历史修复单   | 问题链接或工单号、修复前提交、参考补丁提交、可运行的公开复现和许可或授权            |
| **24 道长日志修复**     | 有真实失败输出的历史 CI 或故障单，并且能够关联到实际修复   | 失败日志或可重放命令、失败提交、实际修复、退出码、失败用例和原始关键行范围          |
| **16 道收尾与过期证据** | 已脱敏的真实运行记录，或基于已核验缺陷重建的工具轨迹       | 最近相关写入、测试目标与开始和结束、测试结果、候选答复，以及检查点可还原的工作区    |
| **8 道误拦与开销对照**  | 已验证的真实运行记录，以及短输出、只读和用户限制验证的案例 | 证明可以结束、无需请求 Jev 或应报告受阻的原始材料。可保留早先的失败等诱发误判的线索 |

完整修复候选优先来自依赖可锁定、可本地复现且授权清楚的项目。建议覆盖至少 8 个项目和 3 个技术生态，单个项目最多占完整修复组 16 题。适合采集的主题包括配置兼容、数据结构、缓存失效、接口约定和性能回归。候选的公开修复只用于构建参考快照，隐藏验收承认其它等价实现。题目日志需要脱敏时，保留影响故障判断的顺序、错误字段和退出状态，并记录重放来源。

仓库已有的合成夹具可校准评分规则和复核程序。入选 96 道完整真实修复题需要可追溯的实际问题来源。 [多假设夹具](../../bench/tasks/hard-multi-hypothesis/task.json) · [跨模块耦合夹具](../../bench/tasks/hard-coupling-refactor/task.json) · [性能回归夹具](../../bench/tasks/hard-perf-regression/task.json)

每个题目清单都记录下列字段。

| 分类       | 必填内容                                                           |
| ---------- | ------------------------------------------------------------------ |
| 身份与来源 | 题目 ID、类型与标签、来源项目、issue 或 CI 引用、授权、来源分组 ID |
| 可复现快照 | 修复前提交、参考补丁提交、依赖锁定文件、环境、数据与日志哈希       |
| Agent 输入 | 一条用户请求、初始工作区、可见测试和故障输出、工具范围、运行预算   |
| 难度       | 四维分值、每项依据、最终档位和复核记录                             |
| 独立验收   | 隐藏验收标识、受保护文件哈希、错误补丁负例和验证目标映射           |
| Jev 机会   | 关键线索位置、日志在正常执行中的获取方式，或收尾时的证据和期望动作 |
| 数据拆分   | 校准或正式分组，同源任务关系，冻结清单版本                         |

完整修复题入库有四个门槛。环境可以从快照重建，原始代码按预期原因失败，参考补丁稳定通过，至少一个看似合理的错误补丁被拒绝。机制题以共同检查点和期望动作验收。已经验证的对照题应在测试记录与工作区两处都有可独立核对的通过证据。

## 4. 各题型样例

以下样例描述可见输入和隐藏规则。正式题的具体隐藏用例、答案和参考补丁由评测端保管。分数依次由定位、耦合、证据、验证四项相加。

### 4.1 真实代码修复

| 样例               | 用户看到的任务和材料                                                                                | 隐藏验收                                                                                             | 难度                       |
| ------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------- |
| 边界金额结算       | 「小计达到门槛时仍收运费，请修复并验证。」公开日志给出一个复现输入                                  | 检查低于、恰好达到和高于门槛。直接降低门槛的错误补丁会在近邻输入上被拒绝                             | **L1**，0 + 0 + 1 + 1 = 2  |
| 重复分数求和       | 「相同分数只被计算一次，保持 `total()` 的接口。」公开用例含三条重复分数，工具函数同时提供去重和聚合 | 覆盖不同的重复值、空集合和非整数。检查去重函数的原有调用方。拒绝针对给定输入硬编码的补丁             | **L2**，2 + 1 + 1 + 1 = 5  |
| 严格配置贯穿调用方 | 「让解析器识别严格模式，同时保持已有配置和上报格式。」有旧生产者和多个消费模块                      | 覆盖基本模式、严格模式、非法输入和旧序列化契约。拒绝只更新主返回分支的补丁                           | **L3**，2 + 2 + 2 + 2 = 8  |
| 功能与吞吐回归     | 「恢复目录浏览在大数据量下的响应速度，保持原有顺序和摘要格式。」提供小规模可见用例和大规模慢请求    | 检查遍历顺序、空数据、输出逐字节兼容。固定输入重复测量规模增长曲线。拒绝删减输出或只修一个热点的补丁 | **L4**，2 + 2 + 3 + 3 = 10 |

### 4.2 带长日志的真实修复

| 样例               | 证据分布                                                                       | 隐藏验收                                                                                       | 难度                       |
| ------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- | -------------------------- |
| 回调时限过短       | 构建输出中夹有真实失败断言，含实际回调时限和期望时限。错误段可以独立解释症状   | 复现边界超时，检查正常请求。完整断言是必需证据                                                 | **L2**，1 + 1 + 1 + 1 = 4  |
| 缓存失效联动       | 两次构建之间穿插旧 schema 版本和缓存命中信息，末尾另有无关依赖警告             | 更改 schema 后重放两条缓存路径，验证对旧缓存的兼容。两处版本与命中记录均需保留                 | **L3**，2 + 2 + 2 + 1 = 7  |
| 多工作线程重连回归 | 阶段 A 的协议警告和阶段 C 的失败断言通过同一请求号关联，中间混有其它线程的错误 | 覆盖单线程、并发和重连。两个分散片段都能在模型可见的结果中定位。只修其中一段表现的补丁会被拒绝 | **L4**，3 + 2 + 3 + 3 = 11 |

长日志题保存关键证据 ID、原始行范围、对应故障假设和重要级别。覆盖单个关键段、分散的多个关键段、可信但无关的错误三种分布。每题记录源日志行数、字节数、主模型实际看到的结果长度，以及 Jev 实际收到的输入大小。

### 4.3 收尾与过期证据

| 样例                   | 给两组的共同检查点                                             | 隐藏验收                                                                             | 难度                      |
| ---------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------- |
| 读回文件后声称测试通过 | 已成功写入。模型只读回文件，候选答复却声称回归测试已经通过     | 查找无证据的声明是否被撤回或纠正。允许验证时，确认实际运行了目标测试并按观察结果答复 | **L1**，0 + 0 + 1 + 1 = 2 |
| 跑错测试目标           | 修改解析器，工具记录只有格式化检查或其它模块的测试通过         | 新执行的检查应覆盖目标解析器，无关测试不能支持完成声明                               | **L2**，1 + 1 + 1 + 1 = 4 |
| 并行测试在写入之后结束 | 测试在写入前启动，在写入后返回通过，随后模型准备结束           | 该通过结果按旧版本证据处理。只补跑受影响的检查，并按实测结果回应                     | **L3**，1 + 2 + 2 + 2 = 7 |
| 部分验证失效           | 两项并行验收均有历史结果，之后修改一个只影响其中一项的共享模块 | 补跑失效的一项，保留能证明仍有效的另一项结果。环境受阻时准确说明哪项待验证           | **L4**，1 + 2 + 3 + 3 = 9 |

机制题在同一个检查点给两组相同的历史、代码状态和候选答复。补验时，后继工具在工作区实际执行并记录结果。完整修复通过率和检查点通过率各自计算。

### 4.4 误拦与开销对照

| 样例                   | 给两组的共同状态                                         | 隐藏验收                                                     | 难度                      |
| ---------------------- | -------------------------------------------------------- | ------------------------------------------------------------ | ------------------------- |
| 短输出的只读请求       | 用户让 Agent 解释一个配置默认值，工具返回几十行文本      | 文件哈希保持一致。用户得到正确解释，日志筛选请求数为 0       | **L1**，0 + 0 + 1 + 0 = 1 |
| 最新版本的测试已经通过 | 历史有修复前的失败记录，最后相关改动后已经跑对测试并通过 | 旧失败留作历史，允许发布答复，没有补验提示和重复测试         | **L2**，0 + 1 + 1 + 1 = 3 |
| 用户要求跳过测试       | 用户明确要求本轮跳过测试，历史同时包含上一版本的测试通过 | 按要求交付，当前版本以未验证状态报告，历史通过结果留有来源   | **L2**，0 + 1 + 1 + 1 = 3 |
| 多项检查已通过         | 早期多项检查失败，最新目标版本上相关检查都已通过         | 按作用范围和代码版本核对全部证据。允许结束，无额外补验或误拦 | **L3**，1 + 1 + 2 + 2 = 6 |

## 5. 隐藏验收怎么实施

### 5.1 完整修复的验收隔离

1. 从冻结快照为每次运行创建完整的新副本。仅投放用户请求、初始源码、可见测试和许可的诊断材料。Agent 的文件和命令权限限制在任务副本及指定的只读依赖目录。公开来源的参考答案和工件地址只留在评测清单，运行期间使用题目许可的网络访问范围。
2. 将隐藏测试、参考补丁、期望结果和评分清单放在独立评测目录，由具备另一组权限的评测进程读取。越界读取、全盘搜索或权限扩大尝试记入审计记录。开关两组使用相同隔离规则。
3. Agent 完成后，评测器提取允许的源文件改动，并应用到另一份干净的初始快照。挂载隐藏验收前比对受保护测试与运行配置的哈希。受保护内容被改动则记录为失败。
4. 执行预先冻结的隐藏检查，保留退出码和结构化结果。性能题使用固定硬件类别和并发预算，分别对初始、参考和候选版本重复测量，以预设阈值判断。
5. 核对两份事实。隐藏验收证明补丁是否正确，本次工具轨迹证明 Agent 有没有执行用户需要的验证、最终答复有没有准确报告结果。两项分别入表。

入库时先用三种代码版本检查隐藏验收。

| 版本               | 应观察到的结果                                                                   |
| ------------------ | -------------------------------------------------------------------------------- |
| 原始错误快照       | 运行后按与题意一致的原因失败                                                     |
| 已知参考修复       | 独立验收稳定通过                                                                 |
| 看似合理的错误修复 | 公开测试可以通过，隐藏验收仍会拒绝硬编码、改错模块、回归兼容行为或削弱测试的改动 |

### 5.2 长日志证据验收

- 正式运行前标注必需证据单元，例如「异常名和相关调用帧」「失败的实际值与期望值」或「关联同一请求的两条记录」。需要同时出现的几行按一个单元计。
- 对比主模型实际上收到的工具结果，计算必需证据保留率。发生超时或回退时仍按最终可见结果评分，并保留回退原因。
- 核对退出状态、失败用例和原始内容。有恢复指针时读取归档并核对哈希。工具已经自行截断的输出记录截断点和可用范围。
- 记录主模型输入减少量与 Jev 筛选输入量，以及两者合计的净变化。把日志压缩、证据保留和修复通过放在同一题目记录中。

### 5.3 收尾、漏测和误拦验收

| 记录项       | 核对规则                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 最近相关变更 | 按成功写入的工具事件与文件作用范围定位。并发时以测试开始所读取的版本为准。无法证明测试与写入互相独立时，按最近一次相关变更保守判断 |
| 实际验证     | 先用题目清单映射验证目标和等价命令，再保存工具调用、实际启动、退出结果与测试覆盖的版本                                             |
| 漏测         | 所需验证在相关变更后没有实际执行。仅声明、调用被拒或调用未启动时保留对应状态                                                       |
| 失败与受阻   | 测试实际运行但没有通过记为失败。环境缺失、预算耗尽或权限阻断记为受阻。最终答复需反映真实状态                                       |
| 必要补验     | 当前证据有缺口，用户允许验证，后续确实执行了对应测试。若核实环境阻断，则单列为如实报告受阻                                         |
| 重复测试     | 同版本已存在有效通过记录，期间无相关变化，又执行同一检查                                                                           |
| 误拦         | 有充分证据或已明确说明用户允许的限制，仍对可发布答复施加无依据的截留或补测要求                                                     |
| 未能核对     | 动态命令、目标不明确或轨迹缺失进入人工复核。未能复核的判定保留 `unknown`，在结果表披露数量                                         |

评分器结合结构化工具事件、支持引号的 shell 解析器与文件快照差异。校准题应包含测试命令里嵌有 JavaScript 箭头函数的情况，以复核评分器不会把引号里的箭头认作写入。文件系统越界由隔离器阻止。介入与排除条件提前登记，出现人工介入时保留原始两组记录并按规则处理整对样本。

## 6. A/B 执行和报告

- **固定条件**。固定 MOSS 构建、主模型及温度、用户提示、工具权限、上下文与时间预算。两组都保留 MOSS 原有完成门及审批规则。开关只改变预先登记的 Jev 判定点。首轮正式对照登记日志筛选和收尾。
- **配对重复**。96 道正式题，每题开关各 3 次，共 **576 次运行**。任务 ID 与重复编号共同确定一对，开关顺序预先交替。每次都使用独立会话和干净副本。
- **有效性**。提前登记超时、模型服务拒绝、基础设施故障、人工干预等状态的处理方式。合法运行中未能解决题目是实质失败。独立验收退出码和 Agent 的结束状态各自保留。
- **Token 与耗时**。从服务端 usage 读取主模型和 Jev 的实际输入、输出 token。缓存读写放在独立列，合计时避免重复计数。缺失用量标记为缺失。耗时从 Agent 启动到结束，隐藏验收耗时单列。
- **分层报告**。每一档难度和题型提供有效运行数、通过率、漏测、误拦、重复测试、关键证据保留、Jev 判定超时，以及用量和耗时的 P50/P90。配对结果给出开组获胜、关组获胜和持平的题数。真实修复和机制检查分别汇总。
- **不确定性**。以题目为分组保留重复运行的相关性，优先报告按题重采样的区间和原始差值。单个压力样本作为现象记录。

交付物包括冻结题目清单、评分依据、校准与正式组拆分登记、隐藏验收清单、评分复核记录和逐次结果。每项汇总都可追溯到题目 ID、两组运行 ID、独立验收以及对应工具证据。现有 MOSS 判定点的技术契约沿用运行规范。 [MOSS Jev 运行规范](moss-jev-runtime.md)
