# Super-agent 收益验证：三轮公平配对

状态：方案冻结，等待真实结果。日期：2026-11-03。基于 `cb7e2250` 的同一 Moss 0.29.1 构建；不改产品 runtime、不改业务契约或 oracle。

用户已批准新增最多 180 次真实模型请求。使用此前指定的接口和 `deepseek-v4-pro`，三轮独立配对，每轮原生和 Super-agent 各自最多 30 次，上限不能互借。原 160 次额度的剩余部分不用于本轮，不做额度外预检。调用失败、压缩、限流、取消均保守计数。

## 对照条件

- 每轮从同一未实现脚手架全新开始，不复用上一轮代码、会话、任务或失败提示。校验两组初始 Git tree 相等。
- 复用原遥测、告警、队列三工单和外部五组 oracle；不因之前失败而修改业务难度、反馈顺序或验收要求。
- 两组均最多三 worker 并发，原生 Task Runtime 均为实际默认 24 轮、5 次修复；agent 配置、权限、输出上限与 thinking 模式一致。上一轮这两个 Task Runtime 参数也是一致的，帮助文案中的旧值不作为执行依据。
- 执行顺序预先固定为 A→B、B→A、A→B，分别使用独立仓库与会话。全局发送间隔同为两秒，记录限流、未知 usage 和完整墙钟时间；不把受控发送间隔误称框架速度。
- 运行中不补写业务代码、不追加提示、不删除模型留下的越界文件、不自动重试整轮。一次启动并自动完成；人工修复次数应为零，两组均适用。
- 此模式只做业务对照，不额外消耗额度运行单侧故障演练。上一轮控制面 10/10 只表示可用，不是收益对照。

## 测量与预先判定

每组每轮记录三个工单的完整通过数、逐组 oracle 结果、HTTP 集成、请求数、已知输入/输出/缓存 token、usage 缺失数、墙钟时间、scope 违规与外部人工修复次数。相同阈值、同一程序汇总，无论谁赢都保留。

1. **业务收益观察成立**：Super-agent 三轮累计通过工单更多，且至少两轮严格优于原生。仅限本任务观察，不推广为普遍能力结论。
2. **调用效率收益观察成立**：两组均完整通过全部九个工单和三次 HTTP 集成，Super-agent 总上游尝试至少减少 20%，且至少两轮也减少 20%。不能以少完成业务换取低消耗。
3. token 只报告已知值。缺 usage 不补零、不估算价格；任一组有缺失就不据此宣称总 token/费用收益。墙钟只列观察值，不作速度胜负标准。
4. 未达到上述条件，结论为“本轮未验证出收益”。若 Super-agent 业务表现更差也直接报告。三次重复只有一个业务族，不能作统计显著或普遍性宣称。

## 既有能力核对

原生 Moss 已有持久化 session inbox、delivery ID 冲突拒绝、会话消息 append-once、worktree、取消与 Task Runtime 恢复。不能把这些能力再次计作新框架独有收益。当前测试不测真人操作时长；脚本自动执行的步骤数不等于人工节省时间。
