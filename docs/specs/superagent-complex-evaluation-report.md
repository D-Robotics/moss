# Super-agent 复杂任务真实模型验收报告

复杂业务未通过，不能声称这次证明了 Super-agent 的复杂开发优势。独立的控制面演练 10/10 通过，证明了接单去重、授权、暂停、取消和显式恢复等行为。

模型演练：2026-11-02；仓库回归：2026-11-02 至 03（Asia/Shanghai）。分支：`codex/moss-superagent-eval`，从已验收的集成提交 `3c9b3ece` 派生。模型：用户指定的 `deepseek-v4-pro`；接口：`https://ai-api.d-robotics.cc/v1`。本次没有接入板卡，没有发布业务服务，没有人工补写模型的业务代码。

## 复杂业务结果

任务为本地“设备运维事件中心”：遥测、告警、通知队列三个独立模块。每个模块含五组外部验收，覆盖去重、重启恢复、状态机、租约和防止陈旧 worker 确认等边界。原版 Moss CLI 与 Super-agent 使用同一模型、原生 runtime、权限、三工单并发和固定业务契约。验收方收集通过的文件并驱动真实 HTTP 集成；这不属于框架自动合并。

| 组别                           | 初始有效编码轮 | 追加修复后 | HTTP 集成              |
| ------------------------------ | -------------- | ---------- | ---------------------- |
| 原生 Moss `task run/resume`    | 1/3            | **2/3**    | 未运行：模块未全部验收 |
| Super-agent + 原生 Moss worker | 0/3            | **0/3**    | 未运行：模块未全部验收 |

最终失败证据：

- 原生遥测：留下授权文件以外的 `probe.mjs`，外部 scope 检查拒绝；续跑另触发任务 token 预算停止。告警、队列均通过五组 oracle，其中告警复用先前已验收任务。
- Super-agent 遥测：残缺 JSONL 尾行恢复组仍报 `CORRUPT_LOG`，其余四组通过。
- Super-agent 告警：跨重启 streak/outbox/ack 组仍报 `corrupt state`，其余四组通过。
- Super-agent 队列：留下额外 `probe.mjs`，scope 检查拒绝，不将后续业务断言算作通过。

上述失败保留原样，没有删除模型留下的越界文件，也没有改动业务 oracle 或放宽验收要求。两个父仓库均保持干净。

## 独立控制面结果

复杂业务未全部验收，因此剩余故障额度单独运行“写入固定回执”任务。模型创建 `receipt.txt`，外部命令同时核对精确内容和文件范围；追问要求在同一授权下复核回执。这个任务不实现三个业务模块，也没有 HTTP 业务集成。

| 场景                                | 实际结果                               |
| ----------------------------------- | -------------------------------------- |
| 相同事件 ID 重投                    | 识别重复，不生成第二张工单             |
| 相同 ID 改写正文                    | 拒绝                                   |
| 未列入授权的 actor                  | 不生成工单                             |
| 暂停后启动新的调度进程              | 没有启动原生任务或模型请求；恢复后继续 |
| 取消独立 canary 工单                | canary 停止，另一工单继续              |
| 已确认原生 TaskID 后 SIGKILL 调度器 | 重启先阻塞不确定任务，不盲目创建新任务 |
| 崩溃前后绑定                        | ticket、worktree、session 保持一致     |
| 人工检查后显式 retry                | 一次重试后通过原生任务及外部验收       |
| 追问事件再次重投                    | 不产生新模型请求                       |
| worker 清理                         | 不需要强制清理孤儿进程                 |

断点是在本地代理中阻止遥测标签请求发送到上游，再强杀调度进程；这是确定性的调度故障注入，不是模拟远端模型服务崩溃。追问生成了同一 ticket 下的新原生任务轮次。取消针对另一张真实启动的 canary 工单。控制面结果来自真实 SDK、CLI worker、SQLite 状态和本机进程，不是脚本模型替身。

## 请求预算与可比性

原额度为 100，用户批准追加最多 60，明确划分为两组各 20 次修复和 20 次故障演练。新增代理同时限制全局及 arm/phase 请求数，失败、限流、压缩请求也计入；全局发送间隔至少两秒，两个入口均显式关闭该网关的 thinking，单次输出上限 8192 token。

| 追加阶段         | 额度   | 预留请求数 | 上游调用尝试 | 已知输入 / 输出 token | 缺失 usage 的上游请求 |
| ---------------- | ------ | ---------- | ------------ | --------------------- | --------------------- |
| 原生修复         | 20     | 19         | 19           | 332890 / 3481         | 4                     |
| Super-agent 修复 | 20     | 20         | 20           | 385279 / 11477        | 0                     |
| 独立控制面       | 20     | 18         | 17           | 202731 / 3144         | 1                     |
| 合计             | **60** | **57**     | **56**       | **920900 / 18102**    | **5**                 |

控制面另有一次请求在本地 gate 被取消，未发送上游，但保守占用额度。表中控制面 17 次上游尝试包含一次 canary 取消请求，它未取得上游响应，是否计费未知。先前阶段按 100 次预留，加上本次 57 次，累计保守计数 157/160。usage 缺失不填零，不估算价格。表中 token 只是服务端明确返回的已知值，包含缓存上下文，不能解释成完整费用。

初始有效轮顺序共享上限，实际原生编码 39 次、Super-agent 23 次，另有一次预检；因此历史状态与预算不对等。追加阶段虽然分别限制 20 次，也无法消除之前的差异。每组只有一个样本，不能据此作模型智力、速度、成本或框架胜负排名。

在有效轮之前还发生过配置失败：网关默认 thinking 与 4096 输出限制使多数输出被推理占满。该轮停止，32 个已完成请求、最多 3 个在途预留及 2 个接口探测均计入原额度；之后统一显式禁用 thinking。没有隐去设置失败，也没有把这类失败解释为业务能力结果。

## 实际发现并修复的问题

真实模型会调用 `task_define` 细化原生任务描述。旧恢复层将这个可变描述与最初授权逐字比较，导致合法工单无法恢复。`0.29.1` 改为核对任务首次创建事件、原始授权与固定验收命令；仍拒绝旧轮次、不明确绑定和验收权变更。

离线回归先在旧构建复现失败，再在修复构建通过；新增断言保证描述细化后的恢复不额外调用模型。独立真实模型故障演练也通过了同一恢复路径。本次没有新增 SDK 导出或依赖。

## 产物与复现

源码包含 [spec](superagent-complex-evaluation.md)、`bench/scenarios/superagent-operations/` 的未实现挑战脚手架、外部 oracle 和 `scripts/bench-superagent.mjs`。脚手架保留未实现状态，模型答案只在被忽略的运行产物里。

本机 `bench/results/` 保存：

- `superagent-operations-live-01/attempt-status.json`：设置失败与保守预算说明。
- `superagent-operations-live-02/summary.json`：初始有效业务轮及各工单 worktree。
- `superagent-operations-live-03/summary.json`：追加修复结果、固定 oracle 哈希检查、原生任务 ID 与 scope 证据。
- `superagent-operations-live-04-controls/summary.json`：独立控制面十项结果、最终工单、操作记录和真实用量。
- 各轮 `model-usage*.jsonl`、worker 日志、`.moss/` 原生时间线与 SQLite 工单库。
- `superagent-operations-validation/`：恢复问题的红绿回归、完整 verify、SDK 示例日志及验收汇总。

运行产物包含会话和本机路径，不推到 Git；真实凭据仅在私有临时文件与代理内存中，worker 只拿本地临时口令。代码、报告和 summary 均未包含真实 Key。

复现完整业务轮需自备私有 `.env`，仅含 `MOSS_BENCH_API_KEY`；不要把 Key 写入命令行：

```sh
npm run bench:superagent -- --env-file /absolute/private.env --max-requests 100
```

独立控制面使用 `--lifecycle-only --max-requests 20`；它不会替代业务验收。已存在的产物可通过 `--resume-from <run-dir>` 续跑，必须另行满足调用者明确授权的总预算。

## 回归与边界

| 检查                                                                                                | 真实结果                                                        |
| --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 旧构建运行新增原生恢复断言                                                                          | FAIL，复现描述细化后的恢复拒绝                                  |

| `node scripts/run-package-tests.mjs --filter superagent`                                            | PASS，4 个测试文件                                              |
| `npm run verify`                                                                                    | PASS，格式、lint、类型检查、441 个测试文件与 CLI/PTY smoke 全绿 |
| `npm run examples`                                                                                  | PASS，3 个离线 SDK 示例                                         |

本机 macOS / Node 24.21.0。verify 的 PATH 前置了真实 Git、装有 pyte 0.8.2 的 QA venv，以及给真实 Clang 指定 MacOSX15.4 SDK 的临时 cc/gcc 包装脚本；没有替换编译结果或修改系统工具链。新增真实模型轮与最终构建的原生 worker SHA-256 一致。未运行 Linux、Windows 或真实板卡验收。

这次能确认的价值是持久化工单控制面可工作，不能确认它让复杂业务开发更强。原版本身已有子代理、worktree、取消、会话恢复和 Task Runtime；这些能力不归为新增优势。此次也未验证自动任务拆解、自动合并、DSH、Web UI 或外部消息适配。
