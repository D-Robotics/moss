# Super-agent 收益对照结果

日期：2026-11-03（Asia/Shanghai）。版本：Moss 0.29.1，同一构建；基于 `cb7e2250`，分支 `codex/moss-superagent-benefit-check`。

**本次只观察到小幅模块交付改善，没有验证出自动完整交付或调用节省。** 同样各 90 次真实模型请求，原生自动验收通过 4/9，Super-agent 5/9。额外人工集成诊断中，两组都能收集到通过真实 HTTP 测试的代码：框架来自同一轮，原生来自不同轮。两组均未在单轮自动完成整套业务。这个结果支持继续小范围实验，不足以证明普遍、稳定的复杂开发收益。

## 主对照：三次独立开始

预先冻结的 [方案](superagent-benefit-check.md) 使用相同遥测、告警、队列契约与外部 oracle，三轮从空白实现重新开始，顺序 A→B、B→A、A→B。每组每轮独立最多 30 次请求，不借用额度、不复用代码和会话、不追加修复提示。

“通过”同时要求：五组代码 oracle、修改范围和原生任务/工单完成门均通过。仅代码正确但自动流程没完成，不计入主通过数。

| 轮次      | 原生通过工单    | Super-agent 通过工单 | 请求：原生 / 框架 |
| --------- | --------------- | -------------------- | ----------------- |
| 1，原生先 | 告警：1/3       | 告警、队列：2/3      | 30 / 30           |
| 2，框架先 | 遥测、告警：2/3 | 告警：1/3            | 30 / 30           |
| 3，原生先 | 队列：1/3       | 告警、队列：2/3      | 30 / 30           |
| 合计      | **4/9**         | **5/9**              | **90 / 90**       |

框架两轮领先、一轮落后，只多交付一张合格工单。它触发了事先定义的“总通过数更多且至少两轮领先”观察规则；这是模块级改善观察，不是统计显著性或框架因果优势证明。9 张工单是三类模块的三次重复，不能解释为九种独立复杂项目。

主流程两组均没有一轮凑齐三张自动完成工单，因此 HTTP 集成前置门未满足，均未运行自动 HTTP 验收；不能把它描述为实际发送 HTTP 后测试失败。

## 请求和 token

| 指标                   | 原生      | Super-agent |
| ---------------------- | --------- | ----------- |
| 真实上游请求           | 90        | 90          |
| 输入 token，含缓存     | 1,098,014 | 1,145,565   |
| 其中缓存读取 token     | 1,024,000 | 1,077,888   |
| 输出 token             | 47,997    | 48,103      |
| usage 缺失             | 0         | 0           |
| 运行中人工补写业务代码 | 0         | 0           |

新增额度 180/180，所有上游返回 HTTP 200，未发起第四轮或额度外探测。原 160 次额度的剩余部分没有使用。两组请求数相同；框架总输入 token 多约 4.3%，输出略多。缓存比例也不同，且没有用户网关账单或计价，不能据此断言实际费用提高或下降。

事先的调用效率规则要求两组都完整通过九个工单与三次 HTTP 集成，再比较是否节省至少 20% 请求，本次未满足。墙钟受两秒发送间隔、配额耗尽后的本地重试和任务完成阶段影响，不用于宣称速度提升。没有真人操作时长实验，脚本步骤数也不计为人工时间节省。

## 补充诊断：存在一套可运行业务代码

这是结束主对照后的额外诊断，不改变主计分或胜负规则。统一检查全部六组产物：只有同一轮三个模块的外部 oracle 和修改范围全部通过，才允许人工收集三个文件并运行原先的 HTTP 集成 oracle，不跨轮挑选代码、不修改模型答案。

只有第 1 轮 Super-agent 满足条件。该轮遥测代码五组外部检查全部通过，但原生任务在 planning 阶段因 `budget_tokens_reached` 停止，框架工单仍为 blocked。这个样本不能算自动完成。因此主计分仍为 2/3，总计仍为 5/9；纯代码 oracle 合计则为原生 4/9、框架 6/9。

验收方作一次人工集成决定，原样复制该轮三个模型文件后，真实本机 HTTP 测试 **PASS**：包含 8 次重复提交、2 条通知、2 次服务重启，以及通知租约/确认与持久化检查。服务器骨架由验收方预先提供，两组使用同一份；框架没有自动合并这些文件。其余五组未满足同一代码门，未强行集成。

产物 `operations-superagent-pair-1.zip` 含三个未修改的模型业务模块、相同服务骨架、公开测试、启动说明与 SHA-256 来源记录。可用 Node 24 在本机运行，不需要模型 Key。这份产物证明有可用代码产出，同时暴露了“代码已正确，自动验收流程仍因预算停止”的交付缺口。

另作对称的跨轮诊断：两组均从自己的三轮结果中，按固定顺序选取每模块第一份通过外部 oracle 和范围检查的代码。原生取到第 2 轮遥测、第 1 轮告警、第 3 轮队列，组装后真实 HTTP 测试也 PASS。框架选出的三个文件均来自第 1 轮，SHA-256 与之前已测样例完全相同，因此引用同一 HTTP 证据，没有将相同代码重复测试算作额外收益。两组均需人工集成决定，未改业务代码，主计分不变。

这证明“人工集成后可运行”不是框架独有结果。跨轮选优属于后验诊断，不能用来计算连续开发所需最少预算，更不能据此声称框架三倍提效。原生的对照产物为 `operations-native-pooled.zip`。

## 实际生效参数与限制

两组 Task Runtime 都是 24 轮、5 次修复；worker 并发、权限、输出上限、thinking=disabled 和 16 轮 agent 硬预算相同。相同的空白 Git tree、固定业务 oracle/契约/驱动 hash 和编译 worker hash均校验通过。

检查还发现，原生 CLI 的 `--max-turns 24` 被全局参数解析为 agent 名义上限 24，框架配置名义上限是 16。不能笼统声称所有名义配置完全相同。两边共同硬预算均为 16；离线边界测试两种设置都恰在 16 次模型调用后以 `budget_turns_reached` 停止。真实运行中每模块全部上游请求的保守上界最多 13 次，任务记录没有 `budget_turns`/`max_turns` 失败标记，未观察到名义差异触发实际停止。该细节保留在 `turn-budget-audit.json`，本报告以等额上游调用和有效预算为比较口径，不将结果表述为全参数无差异的严格因果实验。

原生已有持久化 inbox、delivery ID 冲突拒绝、append-once、worktree、取消与恢复。本次没有将这些能力归为新框架独有收益，也没有把之前控制面 10/10 当作本次收益证据。未运行设备、Linux、Windows 或消息平台接入验收。

## 证据与复现

运行产物均在本机被忽略的 `bench/results/superagent-benefit-check/`：

- `protocol.json`：运行前冻结文件的 hash、顺序和额度。
- `pair-{1,2,3}/summary.json`、`model-usage*.jsonl`：原始验收、请求与 usage；各工单 worktree 保留源码和原生时间线。
- `comparison.json`：配对原始值和预定义程序判定。
- `turn-budget-audit.json`：有效预算核对及名义参数差异。
- `supplemental-integration.json`：统一后验筛选、一次人工集成决定、原样源码 hash 与真实 HTTP 结果。
- `pooled-integration.json`：两组对称跨轮收集的规则、文件来源与集成结果；框架候选与前次样例相同，明确标记证据复用。
- `operations-superagent-pair-1.zip`：可运行的本地演练程序，内含来源说明。
- `operations-native-pooled.zip`：原生组的跨轮人工集成对照程序。

真实 Key 只在私有临时凭据文件和转发代理内存中，未传入业务进程、报告或 Git。运行产物不推到 Git。

```sh
npm run build
node scripts/bench-superagent-benefit.mjs --env-file /absolute/private.env
```

此命令会开启新的三轮、最多 180 次请求，必须由调用者另行授权预算。单元检查可离线运行 `node --test test/superagent-benefit.spec.mjs test/superagent-eval.spec.mjs`；判定逻辑包括“廉价失败不能算效率收益”和至少两轮领先等反例。

驱动退出 0 表示三轮完成，不表示一定有收益，应读取 `comparison.json` 的判定字段。链接中的方案保留执行前冻结原文，当前结果以本报告为准。
