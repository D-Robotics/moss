## 三、沉淀出的稳定决策

### 3.1 产品与边界

- Moss 的目标不是绑定某个机器人品牌或单一 IDE，而是成为可独立使用、也可嵌入宿主产品的 Agent Harness。
- 机器人能力以知识、技能、工具、平台扩展和 Host Adapter 注入；核心运行时保持主机中立。
- CLI/TUI 是官方参考宿主，不应成为核心能力唯一入口；公开 API、子路径导出和宿主契约共同构成嵌入面。

### 3.2 Agent 执行体验

- 长任务必须可观察、可停止、可恢复，并能在上下文压缩后保持目标、计划与关键状态。
- 用户在任务运行中需要能够追加指令、插入 BTW 侧聊、管理排队提示词，而不是只能等待整轮结束。
- 工具结果、审批、重试、降级、子 Agent 进度和最终完成原因必须显式展示，避免“看起来卡住”或“假完成”。

### 3.3 提示词与上下文

- 系统提示词采用稳定的职责分层；人格/项目说明可扩展，但不能覆盖模型诚实性、安全边界和运行时事实。
- 工作区长期约束收敛到 Agent 指令文件；跨会话记忆由 MemoryManager 和工具承载，避免多个 Markdown 记忆源相互冲突。
- 上下文压缩必须保留工具调用配对、目标状态、未完成计划和关键事实，并为确定性、LLM、远端策略提供清晰降级链。

### 3.4 模型与 Provider

- Provider 层应统一流式事件、错误分类、重试语义、token/成本可见性和 thinking-only 异常处理。
- 多 Provider 路由的价值是显式故障转移与策略控制，不是隐藏底层模型；CLI 必须诚实展示实际 Provider/模型。
- 缓存、结构化输出、视觉输入等能力要由运行时能力声明和实际读取共同保证，不能只声明不执行。

### 3.5 工具、安全与设备

- 工具执行遵循最小权限、路径边界、审批策略、密钥脱敏、SSRF 防护和可取消资源生命周期。
- 本地命令、后台进程、SSH、设备诊断、ROS、浏览器与 MCP 工具都应进入同一注册、hook、结果和观测体系。
- 机器人/设备能力是重要差异化，但应保持可插拔；无设备环境下仍须是完整的软件开发 Agent。

### 3.6 质量与交付

- 修复遵循 Declare + Enforce + Test；新增字段必须有实际 reader，行为修复必须有能在修复前失败的回归测试。
- 验证从窄测试开始，最终通过边界检查、卫生检查、基准、构建、类型检查、lint 和完整测试。
- 文档、脚手架、CLI doctor、配置审计和发布检查都属于产品能力，不是实现后的附属工作。

## 四、如何使用本索引

- 产品与技术方案中的“为什么”优先来自这些稳定决策。
- 具体“怎么实现”必须回到当前源码、测试和公开契约核验。
- 历史对话可能包含已经被后续实现推翻的方案，因此不能单独作为当前行为依据。
