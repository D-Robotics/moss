## 4. 思路

### 4.1 自举闭环（Moss 改 Moss，主要的真实使用基准）

1. **选题**：从第 6 节取分数最高的一项，写成**一条用户原话式的任务**。只描述现象和验收，不告诉 Moss 改哪里。
2. **执行**：在 box 的独立 HOME 和 worktree 里运行 `moss`（TUI 或 `-p`），用用户的 key。我只像普通用户那样回答问题、说“继续”，每次介入都记下来。
3. **记录**：dogfood 日志 `rsi/dogfood/<日期>-<任务ID>.md`，固定字段：模型、提交、用时、token（输入、输出、缓存）、轮数、首次正确（是/否）、计划外介入次数、**卡点列表**（现象、证据、疑似位置），以及换成 Claude Code 大概会怎样。
4. **回流**：每个卡点要么进第 6 节成为新的优化项，要么合并到已有项并给出现次数加 1。出现次数就是第 4.2 节里的频次。
5. 这样 Moss 每开发一次自己，就同时做了一次真实使用测试：开发进度和使用体验用的是同一份数据。

### 4.2 怎么选任务

分数 = **影响 × 频次 × 置信 ÷ 成本**，每项 1–3 分：

- **影响**：会挡住某个阶段退出条件，或者是安全问题，记 3；影响某个指标（U、B、C）记 2；其余记 1。
- **频次**：自举日志或真实用户案例（`real-user-cases.md` 的 80 条、论坛问题）里出现得越多，分越高；三家都有的常用功能记 2。
- **置信**：有复现和证据记 3，只有代码审计记 2，只是推断记 1。
- **成本**：按预计改动和评测 token 估。
- **硬规则**：P0 优先；安全回退一律先修；不并行改同一批文件。

### 4.3 怎么度量

| 改动类型                  | 合并前必须通过                                                          | 定期                                |
| ------------------------- | ----------------------------------------------------------------------- | ----------------------------------- |
| 所有改动                  | `npm run verify`、产品检查清单、增量评审                                | 每天的日报                          |
| 动 `src/safety/**` 或打码 | 打码门禁：漏遮集 0 明文、误遮 ≤ main、行数不变、写回不出现 `[REDACTED]` | 架构师的泄漏矩阵                    |
| 能力、提示词、工具        | B1 子集（15 题，约 6.6M token）在噪声带内不退步                         | 每 3 次合并跑一次 B1 全量和 holdout |
| UX 文案、流程             | 相关的 U 项或 C2 旅程复测，en 和 zh 都测                                | 每周一次 U1–U8 全量                 |
| rdk-docs 检索             | blind2 不退步；blind3 只看汇总                                          | 每个版本跑一次                      |

### 4.4 防过拟合

- **盲测集与开发隔离**：blind3 和 holdout 包由 PM 或独立执行者保管，写检索、写提示词的人不读题，只看汇总数字。
- **不写针对单题的规则**：优先通用机制，例如按熵和已知格式打码，而不是按字段名。一项改动如果只在某一道题上起效，不合。
- **任务来源分散**：自举任务来自真实的仓库工作；RDB 题来自真实用户案例；C2 旅程按三家都有的路径设计。
- **判断涨跌看噪声带**：单次结果在带内（B1 SD 0.74 题）不算涨也不算跌。
- **保持精简**：同等效果下，删代码优先。nudge 的消融结果要用来删掉没用的 nudge。

## 5. 原则

**产品**

1. 英文为主，中文完整可选（auto/en/zh）；回答跟随用户提问的语言；同一语言模式内不中英混排。
2. 每个新目录第一次打开时问一次是否信任，信任后完全执行。默认值和配置入口对齐三家的习惯，不一样的地方写明原因。
3. 首次使用不用看文档；报错要给出能直接照做的下一步。
4. 每次合并都过 `product-checklist.md`。

**安全** 5. 不拦截命令，也不拦截读文件。安全靠两点：输出打码（屏幕、日志、会话、答案正文），以及写回保护（不把 `[REDACTED]` 写回文件）。6. 项目文件（`.moss/`、`.env`、AGENTS.md）不能改变网关、key、代理、TLS、模型、审批，未信任时这些都被忽略。`src/safety/**` 只能改得更严。

**评测** 7. 正确性优先：门槛是首次正确率，效率只在双方都首次做对的任务上配对比较；虚报成功记 −1。8. 对照组：传统人工、通用 AI 工具（三家，同一模型、同一网关）、地瓜专家、Moss（加上 Moss-基础消融组）。题目是从真实需求来的端到端应用题。9. 防过拟合：盲测集和 holdout 隔离；用通用机制，不写单题规则；用噪声带判断涨跌。

**工程** 10. 框架保持精简：不重新引入已冻结的子系统；新机制要先有评测证据；能删就删。11. 用户可见的成功信息必须来自真实结果；凭据只从 env 或 `.env` 读，不进日志。

**流程** 12. 任务驱动：一个任务结束就开始下一个，不按固定节奏。开发由 Moss 完成（用户自己的模型 key），不再开 Cursor 任务。13. 评审独立：写代码的不评审自己的代码；评审只看增量，省额度。14. 合入 fork main 要求 `verify` 通过；推 D-Robotics 要在 Mac 上验证；npm 发布要过 P4 门槛，由用户输验证码。删除东西前先问用户。token 每天 ≤ 50M。

## 7. 运作方式

### 7.1 每个任务的流程

1. **选题**：按第 4.2 节，从第 6 节取一项，在 `state.md` 记“开始 O-xx”。
2. **Moss 实现**：在 box 上用 `scripts/selfhost` 跑；模型默认 glm-5.3，备选 deepseek-flash 和 GLM coding plan。分支名 `moss/<O-xx>-<slug>`。
3. **自检**：Moss 自己跑 `npm run verify`，我读 diff。
4. **推分支、开 draft PR**：从 box 推到 fork，用 fork 范围的 token。
5. **独立增量评审**，按类别分给对口的伙伴：
   - 安全 → 架构师（泄漏矩阵）；
   - UX 和文案 → 产品经理（相关旅程，en 和 zh）；
   - 能力 → 测试（B1 子集）；
   - 合并和环境 → 工程师（隔离环境里的 verify）。
     评审只看改动的部分；要改的意见再回给 Moss 改。
6. **合 fork main**：verify 绿、CI 绿、产品检查清单过。用 squash，提交说明写清 O-xx。
7. **dogfood 日志**：写 `rsi/dogfood/`，卡点回流到第 6 节。
8. **下一个任务**：马上开始，任务驱动。

### 7.2 角色

| 角色                   | 职责                                                      |
| ---------------------- | --------------------------------------------------------- |
| 产品负责人（Grok Bot） | 选题；像用户一样操作 Moss；读 diff；合并；推送；写日报    |
| 架构师                 | 安全和架构评审；打码门禁和泄漏矩阵                        |
| 产品经理               | U1–U8 和 C2 旅程；中文文案；产品检查清单审计；保管 blind3 |
| 测试                   | B1、holdout、回归；设计设备任务集                         |
| 工程师                 | 合并后的集成验证；Mac 可移植性；verify 健康               |
| 用户                   | 第 8 节的决策；npm 发布输验证码；保持 Mac 在线            |

### 7.3 什么时候推 D-Robotics

fork main 每积累几次合并，或者有安全修复合入时，就在 Mac 上跑 `npm ci && npm run verify`。通过就快进推到 D-Robotics/moss main，不强推；失败就停止推送，先修。

### 7.4 日报与文档更新

- **日报**：每天 10:26 在对话里发。内容包括合了什么、推了什么；每个自举任务的首次正确、token 和用时；各指标离目标还差多少；需要用户处理的事。
- **兜底检查**：10:26 和 22:26 各检查一次，自举链条断了就接上。
- **更新 `state.md`**：每个任务开始和结束时各记一行。
- **更新本文**：第 6 节在每个任务结束时更新；第 2 节在每次重测后更新；阶段退出时更新第 3 节，并升版本号。
