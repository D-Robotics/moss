# 0.38 前后对比

比的是 Moss `a53d6159`（删除之前的官方 `main`，版本号 0.37.0）和 `7d1f7855`（0.38.0）。
RDK Studio 此前记录的 `9021a042`（0.37.0）只出现在第 2 节和第 5 节。
下文把 `9021a042` 叫钉住版，把 `a53d6159` 叫对照。
删掉的内容见 [Moss 与 Pi 的通用能力对照](../pi-parity.md)第 1 节。

五组测量用的负载各不相同，分开读：

- **harness 每回合开销。** 桩模型，不发网络请求，量的是 harness 自己花的时间。
- **真实模型基准。** 27 道题各 3 个样本，模型 `xiaomi/mimo-v2.6-pro-ultraspeed`，temperature 0。
- **交替运行。** 两个构建逐个样本轮换，用来分开 harness 和模型服务各自对每回合时间的影响。
- **RDK Studio 层。** Studio 自带的质量探针，在 0.37 和 0.38 上各跑一遍。
- **TUI 体感。** 伪终端里回放按键，量首屏就绪、回显、首帧和中断的响应时间。

## 1. 结论

| 问题                     | 答案                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| harness 每回合变快了吗   | 重读同一文件时更快，快 13% 到 14%。无工具回合差 3.5%，读不同文件差 2.5%，后两项没有做显著性检验 |
| 同样的任务模型少做事了吗 | 是。80 对双方都通过的样本里，回合少 10.4%，工具调用少 8.6%，输入 token 少 7.6%                  |

| 墙钟变短了吗 | 交替运行下更短，少 20%，区间 0.73 到 0.87。先后跑的那组多 13.3%，那是服务延迟漂移和一个样本造成的 |

## 2. harness 每回合开销

桩模型，同一台机器，两个构建交替运行。这一节的钉住版是 `9021a042`。

| 负载                        | 钉住版            | 0.38              | 差值              |
| --------------------------- | ----------------- | ----------------- | ----------------- |
| 无工具回合，单次            | 508 毫秒（40 轮） | 490 毫秒（40 轮） | 差 3.5%，未做检验 |
| 12 回合，每回合重读同一文件 | 1558 与 1527 毫秒 | 1341 与 1307 毫秒 | 快 13% 到 14%     |
| 12 回合，每回合读一个新文件 | 1398 毫秒         | 1363 毫秒         | 差 2.5%，未做检验 |

后两行各 60 轮。重读那一行跑了两种先后顺序，所以钉住版和 0.38 各有两个数。

这一项一开始是反的。写回修复之前，0.38 在重读负载上比钉住版慢 9% 到 11%。
原因是上下文折叠去重之后，harness 立刻把整个会话写回存储，重写时对全部字符串做脱敏，
脱敏每次都重新读盘取已知的密钥值。现在改为运行结束时写一次。12 回合的运行里，
整会话重写从 10 次降到 1 次。修复在 `7d1f7855`。

重读那一行两边的工作量也不相等。钉住版 12 次读取里有 4 次被工具循环守卫拦掉，0.38 读满 12 次。
所以这个差值偏保守。

持久化没有因为推迟写回而受损。在 0.38 上探了四步：

- 首次运行退出码 0。会话文件里 1 条快照、26 条消息、12 对工具调用与结果。
- 新进程用 `--continue` 接上，首个请求 54925 字节，折叠结果保留。
- 运行中 `kill -9`，只有 10 条追加消息，没有快照。
- 强杀之后再用 `--continue`，运行跑完。会话重写为 1 条快照、27 条消息，
  悬空的工具调用由原有的修复路径补上结果。

钉住版没有跑这组探针。

还有两处没有追到底：

- CPU profile 里，钉住版的 token 估算函数自身时间 478 毫秒，0.38 是 18 毫秒。
  其中 137 毫秒来自已删除的 steering 评估，341 毫秒挂在上下文准备之下。
  但两个构建里这个函数逐字节相同，微基准每次调用中位数都是 3.6 毫秒。这部分差距没有完全解释。
- 取已知密钥值的函数没有缓存，是会话存储剩下的开销。它在冻结路径 `src/safety/known-secrets.ts` 里，没有改。

**运行时判官的开销。** Jev 判官默认开启。无工具单回合，默认开启时中位 1317 毫秒，
显式关闭 558 毫秒，各 6 次交替运行，默认路径多约 760 毫秒。测量时机器同时在跑基准。
12 回合时单次样本互有高低，没有得到稳定差异。代码没有动，去留见对照文档第 1 节。

## 3. 真实模型基准

两个构建各跑 27 道题，每题 3 个样本。对照臂在 11 月 26 日 07:27 到 07:59 跑完（北京时间）。
0.38 分两段跑完，08:04 到 08:40。两边都没有超时，也没有被重试的样本。

按题和样本配对，80 对双方都通过。比例是 0.38 的总量除以对照的总量。

去掉这个样本，墙钟是 1839.7 秒对 1866.3 秒，比例 1.0145。

把墙钟按回合摊开，80 对全部算进去是每回合 2.67 秒对 3.38 秒，每回合输出 419 对 457 token。
去掉那个样本是 2.66 秒对 3.09 秒，多 16.2%。每回合输出 417 对 442，多 6.0%。

## 8. 读这些数字要知道的事

- 第 3 节的两个构建是先后跑的，模型服务的延迟变化混在墙钟里。墙钟以第 4 节的交替运行为准，它只覆盖 8 道短题。
- 0.38 是一整批删除合在一起的结果。哪一项删除贡献了多少，没有单独隔离。
- 每道题 3 个样本，一个模型，一台机器。通过率上差一个样本分不出来。
- 运行器只透传白名单里的环境变量，两边都没有关判官，所以判官两边都开着，对照是公平的，
  但墙钟里有外部服务的网络延迟。
- 第 2 节的钉住版是 `9021a042`，第 3 节的对照是 `a53d6159`。两者都是 0.37.0，不是同一个提交。

## 9. 产物

结果在 `bench/results/`，不入库。第 3 节读 `perf-main-full/` 和 `perf-head-all/`。
第 4 节读 `perf-interleaved/` 下的 `base/`、`head/` 和 `ledger.json`。
第 5 节读 `perf-pin/` 和 `perf-head/`。三节用同一条命令算出来：

```
node scripts/compare-bench-results.mjs bench/results/perf-main-full bench/results/perf-head-all
node scripts/compare-bench-results.mjs bench/results/perf-interleaved/base bench/results/perf-interleaved/head
```

配对的键是题目加样本号。同一个键出现两次时脚本直接退出，因为那会让一行对照配上多行。
交替运行由 `scripts/interleave-bench.mjs` 驱动，它每次调用只跑 1 个样本，合并时写回真实的样本号：

```
node scripts/interleave-bench.mjs <对照的 dist/cli.js> base <0.38 的 dist/cli.js> head 4 bench/results/perf-interleaved single-edit test-fix-loop
```

`summary.json` 里的 `meta.gitSha` 是运行目录的提交，不是被测构建。被测构建由启动时的 `MOSS_BENCH_CLI` 决定。
TUI 体感的报告是 `bench/results/tui-feel-<时间戳>-<进程号>.json`，每次运行一份。
