Categories: **Added** · **Changed** · **Fixed** · **Removed** · **Internal**

## [Unreleased]

### Added

- **Resume now restores the active goal's UI state**: `resumeSession` reloaded the conversation messages but never called `agent.getGoal`, so although `MossAgent` correctly re-loaded the goal from persisted checkpoint messages (the LLM still knew about it), the TUI's goal activity indicator stayed empty and `runCount` restarted at 0 — the user couldn't see that a goal was active after resuming. `resumeSession` now fetches the goal for the resumed session and, if it's `active`, calls `activateGoalActivity(goal)` and posts a transcript line ("Active goal restored: <objective>"). The continuation itself resumes naturally on the user's next prompt (`runPrompt` → `scheduleGoalContinuation`); we don't auto-schedule during resume to avoid a `sessionKey` state race right after `switchToSession`.
- **`/model` switch now re-detects the new model's context window** (auto-detection requirement): `switchModelForSession` set `agent.config.model` / `provider` but never updated `contextTokens`, so after switching from a 200k model to a 32k model the ctx-usage status bar, compaction threshold, and pruning all kept using the old model's window until the agent restarted. After a successful switch, moss now calls `resolveContextTokensForModel` (API probe of the provider's `/v1/models` or Ollama `/api/show` → name-pattern fallback) and updates `agent.config.contextTokens` + `runtime.config.contextTokens`; the status-bar denominator refreshes immediately and the next turn's `createAgentLoopRun` (which reads `this.config.contextTokens` fresh) uses the correct window. A transcript line reports the detected window + source (e.g. "Context window: 128k tokens (provider-api) for llama-3.1-70b"). The probe is async with a 4 s timeout and runs fire-and-forget so `/model` returns instantly. A user-pinned `contextTokens` override (`contextTokensSource` of `cli` / `MOSS_CONTEXT_TOKENS` / `config`) is respected and not re-detected. The underlying `resolveContextTokensForModel` was already covered by `model-context-window.spec.mjs`.
- **`edit_file` tool results now render as a colored inline diff in the TUI** (parity with `apply_patch` / `write_file`): when the user expands a tool call (Ctrl+O) and the agent ran `edit_file`, the `ActivityItemLine` previously fell through to raw JSON or `item.result` — the user could not see what text was actually replaced. The expanded view now reuses the LCS-based `diffLinesForApproval` helper (from `approval-detail.ts`, already used for the pre-approval diff) to render `old_string → new_string` as `- ` removed (red) / `+ ` added (green) / `  … (N unchanged)` context (dim) lines, capped at 80 lines. The headline already shows the file path via `toolHeadline`, so the diff lines complete the "which file, which lines changed" picture that Claude Code shows. Falls through to the result/JSON branches when the diff is too large (>400 lines, `diffLinesForApproval` returns null) or the input lacks `old_string`/`new_string`. Verified by a new `approval-detail.spec.mjs` (the helper previously had zero tests): basic replacement, pure insertion, pure deletion, identical input, >400-line null fallback, and the empty-old-string edge case.

### Fixed

- **Provider connection-error hints now actually reach the user (TUI run errors, slash-command failures, headless output, tool results)**: `connection-error.ts` carefully classifies a fetch failure's cause code (ENOTFOUND / ECONNREFUSED / ETIMEDOUT / ECONNRESET / EHOSTUNREACH / CERT_* / EPROTO / PROXY…) into a specific, actionable `.hint` ("DNS lookup failed for host — check network and DNS", "Connection refused by host — server not running or wrong port", "TLS/SSL certificate error — set NODE_TLS_REJECT_UNAUTHORIZED=0", etc.) and attaches it to a `MossError`. But two helpers — `errorMessage()` (errors.ts, used by 123 call sites including the TUI run-error path, `/compact` `/sessions` `/diff` `/memory` catches, headless print, and tool-result text) and `describeError()` (provider/errors.ts, used by the agent loop to build `agent_error` / turn-error event payloads that the TUI renders verbatim) — both returned only `err.message`, silently dropping `.hint`. `formatMossError()` was the one helper that included the hint, but it was exported and never called anywhere. So the entire connection-hint classification (two prior commits' work) was invisible to users — a DNS failure showed "fetch failed for api.deepseek.com (ENOTFOUND: …)" with no hint that it was a DNS problem or what to do. `errorMessage()` and `describeError()` now append `\n→ <hint>` for any `MossError` carrying a hint (message format unchanged otherwise — no `[CODE]` prefix clutter, plain Errors and non-Errors untouched). The TUI's two run-error paths (`event.type === 'error'` and the `catch` around `streamChat`) switched from `String(event.error)` / `err.message` to `errorMessage(...)`, so streaming/turn errors surface the hint too. Verified by a new `errors.spec.mjs` (the module previously had zero tests): hint propagation through `errorMessage` / `describeError` / `formatMossError`, plain-Error message-only, non-Error `String()` fallback, and `errorMessage === describeError` agreement on MossErrors. Full suite (58 files) passes.
- **TUI hid all tool progress by default — users saw only a spinner and could not tell whether the agent was working or hung**: the Ink TUI initialized `detailMode` with `process.env.MOSS_CLI_DETAIL || 'quiet'`, hardcoding `'quiet'` when the env var was unset. In quiet mode the TUI suppresses tool-activity labels and completed-tool result lines, so during a turn that called `read_file` / `exec` / `edit_file` the screen showed nothing but the `Moss ❯▪` spinner — no tool names, no progress, no feedback. A tool running 5–10 s looked identical to a frozen process, and users pressed Esc to interrupt a healthy run. The non-TUI output path (`output.ts:resolveCliDetailMode`) already defaults to `'progress'` and honors `--quiet` / `MOSS_CLI_DETAIL` / `MOSS_VERBOSE_CLI` / `MOSS_SHOW_THINKING`; the documented default (`help.ts`) is `progress`. The TUI now sources its initial `detailMode` from `resolveCliDetailMode()` too, so the TUI and `moss --no-tui` agree, `moss --quiet` actually quiets the TUI, and the default shows tool progress. The `/detail` command and `setDetailMode` are unchanged (still switch at runtime). Typecheck + `cli-tui.spec.mjs` + `cli-output.spec.mjs` (which already covers `resolveCliDetailMode`'s default=`progress`) pass.
- **Abort during tool execution no longer discards completed tool results**: when `abortSignal` fired mid-execution (e.g. user pressed Ctrl-C while a parallel tool group was running), `executeAgentLoopToolCalls` noted ALL tool calls as pending-aborted and returned `{pendingMessages: []}` — even tools that had already completed. Their results were never persisted, and the next run (resume) synthesized abort tool_results for ALL tools, telling the LLM "everything was cancelled" when some had succeeded. The abort branch now (1) persists the completed `toolResults` via `appendMessage` (best-effort), and (2) notes only the tool calls that never produced a result as pending-aborted. On resume, `consumePendingAbortedToolSyntheticMessages` synthesizes abort results only for the unfinished tools — the LLM sees which tools succeeded and which were cancelled.
- **Project config could silently lower the user's safety settings**: `mergeConfigFiles` spread the project `.moss/config.json` over the user's `~/.config/moss/config.json` for ALL top-level fields, so a cloned repo could override `safetyMode`/`approvalPolicy`/`trustedTools`/`deniedTools` — e.g. a project setting `approvalPolicy: 'never'` or `safetyMode: 'full-access'` would silently auto-approve / widen access against the user's explicit, safer choice. Safety-sensitive fields now use user-priority (the user's explicit setting wins; the project value is used only when the user hasn't set one). Non-safety fields keep project-priority (project-specific config like `model`/`provider` still wins, unchanged). CLI flags and env vars override both (resolveCliConfig). Verified by a new `cli-config-merge.spec.mjs`.
- **`runAgentLoop` burned one LLM call when the user aborted between the tool loop and follow-up fetch**: after the inner tool loop exited (all tool calls resolved) and before `getFollowUpMessages` was called, there was no `abortSignal` check. If the user pressed Ctrl-C in that window, follow-up messages were fetched and a new outer-loop iteration started — wasting one LLM call the user had already cancelled. Added `if (abortSignal.aborted) break outerLoop;` before the follow-up fetch, matching the existing start-of-iteration abort check. (The review also flagged abort-during-tool-execution discarding completed tool results, and `flushAssistantBuffer` failure dropping assistant messages — both real but they change abort/persistence semantics and need a larger redesign; deferred.)
- **TUI prompt editor froze on huge pastes**: the `input` state in `PromptEditor` was an unbounded string, so pasting a large blob (a 1MB base64 image, a whole source file dropped into the editor) lived in React state and froze the TUI while Ink diffed hundreds of KB on every render. `applyEdit` now caps the value at `MAX_PROMPT_INPUT_CHARS` (50KB — far above any reasonable prompt; for larger content users should attach a file with `@file`, which streams as an attachment, not via inline editor state), truncating the value and clamping the cursor. (The subagent review also flagged `ctxPct` showing >100% — refuted: when `used > total` the context is genuinely over budget, so the red >100% display is correct, not a bug; and `toolsExpanded` merging tool + thinking expand — a UX change, not a bug.)
- **CodeGraph MCP connection used the default 30s request timeout**: `autoRegisterCodeGraphTools` built the codegraph MCP server config without `requestTimeoutMs`, so it fell back to the MCP default (30s). Structural queries like `codegraph_trace` / `codegraph_impact` on large repos can exceed 30s and surface as opaque connection errors. The codegraph config now sets `requestTimeoutMs: 120_000`. (The subagent review also flagged `MOSS_CODEGRAPH_CMD` env injection — low severity: controlling the parent process env already implies arbitrary-code ability; and concurrent-init locking / stale-index detection — those hinge on the external `codegraph` binary's own behavior, which moss can't fix from the wrapper.)
- **`vision_analyze` URL fetch had no SSRF defense**: `fetchImageFromUrl` only checked `^https?://` and fetched any URL, so a prompt could drive the LLM-callable `vision_analyze` to `http://169.254.169.254/latest/meta-data/` (cloud metadata), `localhost`, or RFC-1918 hosts and exfiltrate the response via the image block. It now resolves the URL hostname through `isPrivateHost` (reused from `web-fetch.ts`) and refuses private/loopback/link-local targets before fetching, mirroring `web_fetch`'s default anti-SSRF blocking. Verified by a new `vision-ssrf.spec.mjs` (cloud metadata / localhost / 127.0.0.1 / 10.x / 192.168.x all refused). Note: the subagent review also flagged `attachments.ts` path traversal — refuted on verification: `attachments.ts` is the user-CLI `@file` path (user-initiated, reads the user's own file), and the LLM-callable `vision_analyze` file path already sandboxes via `assertSandboxPath`. EXIF stripping (privacy) left as a follow-up — needs an image dep.
- **teaching layer swallowed all LLM errors silently + cache grew unbounded**: `createTeachingHooks` ran every teaching LLM call as fire-and-forget with `} catch { return null }` and `.catch(() => {})` — a teaching LLM timeout/failure produced no log, no metric, no event, so users and operators couldn't tell teaching was silently degrading to empty/heuristic annotations. The inner `llmJsonObject` catch and the two outer annotation-task catches now `log.warn` the failure (via `getRootLogger().child('teaching')`). Separately, the per-instance annotation cache only skipped expired entries on read (TTL check) without ever deleting them, so a long session with teaching on accumulated stale keys indefinitely; `setCacheJson` now sweeps expired entries when the cache exceeds 256 entries. Teaching is opt-in (`depth='off'` by default, not wired into `cli-main`), so the cost/unbounded-call findings are lower urgency, but the silent-error + cache-leak fixes apply whenever teaching is enabled.
- **eval: `exactMatchMetric` was a substring test; `defaultMetrics` were silently ignored; `eval` tool was mis-classified as readonly**: three bugs in the eval framework. (1) `exactMatchMetric` used `response.includes(expected)` — a substring test — so `"pineapple"` matched `"apple"` with score 1.0; now an actual exact match (`trim` + `===`), since substring matching is what `containsAll`/`containsAny` are for. (2) `EvalRunner.evaluateCase` looked up `(testCase as any)._suite` to merge `EvalSuite.defaultMetrics`, but nothing ever set `_suite` on a case — so suite-level default metrics were silently ignored; `evaluateCase` now takes the suite as a parameter (passed by `runSuite`) and merges via `getMetricsForCase`, with case-level metrics overriding same-named defaults. (3) the `eval` tool had `sideEffectClass: 'readonly'`, but `define` mutates an internal `suites` Map — `readonly` classified it as parallel-safe (race on the Map) and skipped approval; changed to `runtime_state` (matching `plan_step`). Verified by a new `eval.spec.mjs` (the module previously had zero tests): exactMatch correctness, defaultMetrics application + override. `semanticSimilarityMetric` (Jaccard token overlap, not semantic) renamed to `tokenOverlapMetric` in a separate change (see Changed below).
- **`validateJsonSchema` overflowed the stack on pathologically deep schemas + `enum`/`const` were key-order-sensitive**: the schema validator is purely recursive with no depth limit, so an LLM-provided schema nested beyond the call-stack limit (~10k) crashed the process with `RangeError`; and `deepEqual` used `JSON.stringify`, so `enum`/`const` checks compared `{a:1,b:2}` and `{b:2,a:1}` as unequal and falsely rejected valid output whose key order differed from the schema's. `validateJsonSchema` now takes a `depth` parameter (capped at `MAX_SCHEMA_DEPTH = 64`, exported) and returns a clean "schema nesting exceeds max depth" error instead of overflowing; `deepEqual` is now a proper structural compare (key-order-insensitive, recursive, array-aware). Verified by a new `schema-validator.spec.mjs` (the module previously had zero tests): key-order-insensitive enum/const, over-depth schema rejected (not stack-overflowed), boundary depth still validates.
- **`exec_background` lost tail output for fast-exiting processes**: the child-process listener used `child.on('exit', …)`, but Node fires `exit` the moment the process exits — the stdout/stderr pipes may still hold buffered data the parent hasn't drained. Settling on `exit` therefore snapshot `proc.buffer` before all output arrived, so `exec_logs`/the settle message showed an incomplete tail. Switched to `child.on('close', …)` (fires only after all stdio streams are drained), matching `run-process.ts:127`. Verified by a new `background-exec.spec.mjs` (the subsystem previously had zero tests): full output capture for a fast-exiting process, `exec_stop` kill escalation, and the `isCommandDangerous` safety gate.
- **`fleet_batch exec` skipped the dangerous-command safety gate**: `device_exec` runs `isCommandDangerous` before executing on a single device, but `fleet_batch action="exec"` did not — so `fleet_batch exec "rm -rf /"` would fan a destructive command across every device in the fleet with no gate. `fleet_batch exec` now runs the same `isCommandDangerous` check and returns `Command blocked (fleet-wide): <reason>` before dispatching to any device. Verified by a new `batch-device.spec.mjs`.
- **`fleet_batch gather` shell-injected the file path**: `gatherFileFromDevice` built the remote command as `cat "${filePath}"` with the LLM-supplied path interpolated into double quotes — `$(…)`, backticks, and `"` could inject device-side commands. It now uses `shellEscape(filePath)` (single-quote POSIX escaping from `ssh-utils.ts`), the same primitive the other device tools use. Verified by a `shellEscape` injection-safety case in `batch-device.spec.mjs`.
- **`pi-ai` watchdog timeout message was misleading on inter-event stalls**: `startFirstEventWatchdog` used a single `firedByTimeout` flag for both the first-event deadline (no event within the initial window) and the inter-event deadline (stream stalled mid-response after emitting some events). `translateError` always returned a `PiAiFirstEventTimeoutError` whose message said "在 Ns 内未吐出任何流事件" — factually wrong for an inter-event stall, which had already emitted events. The watchdog now tracks which phase fired (`firedPhase: 'first' | 'inter'`); `PiAiFirstEventTimeoutError` takes a `phase` and the inter-event message reads "流在中途停滞——已吐出部分事件后 Ns 内无新事件" instead of "未吐出任何流事件". `instanceof` checks are unchanged (same class). Verified by a new `pi-ai-watchdog.spec.mjs` covering both phases.
- **`isCommandDangerous` regex bypasses — `rm -rf` of root/home evaded detection**: the `rm` pattern `/\brm\s+-[a-zA-Z]*r[a-zA-Z]*f?\s+[/~]/` anchored "recursive flag then immediately `[/~]`", so three real-world variants slipped through and would only be caught by the approval layer (not the safety backstop): `rm -rf -- /` (the `--` end-of-options marker between flags and path), `rm -rf $HOME` / `rm -rf "$HOME"` / `rm -rf ${HOME}` (shell-expanded home), and `rm --recursive --force /` / `rm -r --force /` (long `--recursive`, or `--force` after the short flag). The pattern now tolerates the `--` separator, additional short/long options around the recursive flag, optional quotes, and `$HOME`/`${HOME}` expansion — for both short (`-rf`/`-r`/…) and long (`--recursive`) forms — while preserving the existing "block `rm -rf /<anything>`" stance and NOT false-positiveing on `rm -rf somedir/`. Also broadened three sibling patterns that had the same shape of gap: `chmod 777 /` now catches `chmod -R 777 /` and `chmod 777 /etc/…`; `git push --force` now catches `git push -f`; and a fork-bomb pattern (`:(){ :|:& };:`) was added (previously unmatched). Verified by new `cli-security.spec.mjs` cases for every bypass variant plus a no-false-positive case.
- **`sanitizeSecrets` did not mask `Authorization: Bearer <token>`**: the credential-value pattern requires a secret keyword (`password`/`token`/…) *before* `[:=]`, but in `Authorization: Bearer …` the keyword (`Bearer`) follows the colon — so `curl -H "Authorization: Bearer sk-ant-…"` was not masked in approval prompts / logs. Added a dedicated Bearer-token rule (masks the token value). Verified by a new `cli-security.spec.mjs` case.
- **`MultiProviderRouter` penalized fallback providers for user-initiated cancels**: when the primary failed with a retryable error and the user aborted (Ctrl+C) during a fallback's in-flight request, the abort propagated to the fallback's `fetch` (which threw an `AbortError`), and the router's fallback `catch` ran `if (!classification.retryable) health.unhealthyUntil = now + cooldownMs`. Since `classifyLlmError` maps an abort to `user_abort` (`retryable: false`), the fallback was marked **unhealthy for 60 s** for a cancel that was not the provider's fault — so a user who pressed Ctrl+C during a slow fallback would find that provider skipped on the next call. The fallback loop now (1) early-exits when `opts.abortSignal` is already aborted, and (2) propagates a `user_abort` immediately without marking the provider unhealthy. Verified by a new `multi-provider-router.spec.mjs` (the module previously had zero test coverage): primary-retryable→fallback-success, user-abort-during-fallback propagates and does NOT mark unhealthy, non-abort non-retryable failure still marks unhealthy.
- **Skill auto-learning persisted raw conversation text — including pasted secrets — into `SKILL.md`**: `ConversationSkillLearner.buildSkillMarkdown` wrote `userMessage` and `assistantText` verbatim into the skill draft (title, description, `example_query`, result summary, "原始需求"). `redactInput` only redacts structured tool-input *keys* (`api_key`/`token`/…), not free text, so a user who pasted "my key is `sk_live_…`" into the conversation would have that key written to `.moss/skills/` and re-injected into the agent prompt whenever the skill matched. `buildSkillMarkdown` now runs both free-text fields through a new `redactSecretsInText` (exported from `memory-manager.ts`, sharing the canonical `MEMORY_SECRET_PATTERNS` so the patterns cannot drift from `validateMemoryWriteContent`), replacing each match with `[redacted]` (global, so the same secret pasted twice is redacted in both places). Verified by a new `conversation-skill-learner.spec.mjs` covering secret-in-userMessage, secret-in-assistantText, double-paste global redaction, and clean-content-preserved.
- **`MemoryManager.add`/`update` did not enforce secret validation at the write boundary**: `validateMemoryWriteContent` existed and was exported, but only the CLI `memory` tool called it before writing — `add()` and `update()` themselves accepted any content. Any caller that forgot upstream validation (self-learning memory, knowledge-card extraction, a future write path) could persist a secret/API key to disk, where `buildDigest()` would later inject it into the system prompt. `add()` now validates `content` and `update()` validates `patch.content` at the top of each method, throwing `memory add/update rejected: <reason>` on a `MEMORY_SECRET_PATTERNS` / `MEMORY_INJECTION_PATTERNS` hit. The CLI path still validates upstream (no behavior change for legitimate content); this is the defense-in-depth backstop. Verified by a new `memory-manager.spec.mjs` case asserting secret-shaped add/update reject and do not mutate existing entries.
- **`web_search` Bocha backend used the wrong HTTP method — keyed search never worked**: `createBochaSearch` issued `GET https://api.bochaai.com/v1/web-search?q=…&count=…`. Bocha's official API is `POST` with a JSON body (`{query, count, summary, freshness}`); the GET form is not accepted, so every keyed request failed and silently fell through to the keyless chain. A bundled or configured `BOCHA_API_KEY` therefore never produced a single successful search — users got keyless results regardless. The backend now POSTs a JSON body `{query, count, summary: true}` (the `freshness`/recency field is added in a separate change) with `content-type: application/json`. Verified by unit test asserting `method === 'POST'` and the JSON body carries `query`/`count`/`summary`; the keyed path's real network behavior is not exercised here (no bundled key in this tree), only the request shape.
- **`web_search` re-registration in `cli-main.ts` silently dropped the bundled Bocha key**: `registerBuiltinTools` registered `web_search` with the bundled `bochaApiKey`, then `cli-main.ts` re-registered `createWebSearchTool({ region })` — and `ToolRegistry.register` overwrites by name, so the locale-derived region was added but the bundled key was lost, dropping every search back to the keyless chain. The re-registration now merges both: `{ ...(region ? {region} : {}), ...(bundledBochaKey ? {bochaApiKey: bundledBochaKey} : {}) }`. `bundledBochaKey` is now exported from `builtin.ts` so the re-registration can re-supply the same key the builtin loaded.
- **`JsonlSessionStore.replaceMessages` accumulated dead bytes without bound**: each `replaceMessages` call appended a full `state_replace` snapshot line and never pruned the prior ones, while replay ignores everything before the latest `state_replace`. So over a long session the on-disk file grew ~ (history size) × (number of replaces) — every compaction/checkpoint/goal/repair replace wrote the whole history again as dead bytes that replay would never read. `replaceMessages` now atomically rewrites the file (temp file + `fsync` + `rename`) to just the new snapshot line, pruning all superseded `state_replace` and `message` lines. `appendMessage` stays incremental (one line per message); the per-turn write path was already O(n) total — only the snapshot path was unbounded. Verified by a new `jsonl-session-store.spec.mjs`: 20 growing replaces leave exactly 1 `state_replace` line and the correct 20-message live replay.
- **Foreground sub-agent `timeoutMs` was silently ignored**: `toolCtx.spawnSubagent` (the foreground path used by `create_subagent` without `background: true`) invoked `subAgentRunner` directly, bypassing the orchestrator's `runSingleChild` — which is the only place timeout enforcement existed for fan-out. So a foreground sub-agent whose model hung or looped would keep burning tokens until `maxTurns` or a parent abort, ignoring the `timeoutMs` the caller passed. `spawnSubagent` now builds its own `AbortController` that aborts on `timeoutMs` (default 120 s) **or** when the parent signal aborts, passes `controller.signal` to the runner, and clears the timer in a `finally`. The runner already converts an aborted signal into a failed `SubAgentResult`, so the parent receives a clean timeout failure instead of an unbounded wait. (Mirrors `runSingleChild`'s proven timeout structure; a dedicated subagent-timeout integration test is a follow-up — it needs a subagent harness that doesn't exist yet.)
- **Parallel tool groups bypassed the host approval hook**: when a turn produced a parallel-safe group of tool calls (readonly tools executed concurrently via `Promise.allSettled`), `executeOneToolCall` was called with `checkToolApproval: undefined`, so the host's approval callback was never invoked for those calls — no `tool_approval_request`/`tool_approval_resolved` events, no audit trail, no deny path — while the same tools executed serially went through the hook. The parallel branch now passes `checkToolApproval` through, matching the serial path. Parallelism is preserved because parallel groups only contain readonly tools (filtered to readonly above), whose approval typically resolves to `null` (no prompt); the hook now runs per-call inside each concurrent `executeOneToolCall` rather than being skipped.
- **`SessionManager` cache returned stale context after truncation/compaction**: `truncateTrailingAssistant`, `truncateForRegenerate`, and `appendCompaction` mutated the session entry tree but never cleared `state.cachedContext`. The next `getContextMessages` call returned the *pre*-mutation message list (the cache only checks `cachedContext !== null`, with no version check), so a truncated or compacted session could keep feeding stale context to the model until the cache was evicted by an unrelated write. All three mutation paths now set `state.cachedContext = null`, matching the existing append path's invalidation. (`SessionManager` is a public API not exercised by the CLI, but any host embedding moss that drives truncation/regenerate/compaction through it was affected.)

### Changed
- **`semanticSimilarity` eval metric renamed to `tokenOverlap`**: the metric was named `semanticSimilarity` but its implementation is Jaccard token-set overlap (lexical) — not embedding/semantic similarity. The name gave users and the LLM a wrong mental model (a rephrase scores 0 despite identical meaning). Renamed the function `semanticSimilarityMetric` → `tokenOverlapMetric` and the LLM-facing metric name `semanticSimilarity` → `tokenOverlap` (registration, type union, tool description) across `metrics.ts` / `eval-tool.ts` / `eval-driver.ts` / `eval/index.ts` / `src/index.ts`. **Breaking** for any eval config that referenced `semanticSimilarity` by name — a repo-wide grep found no skills/docs/tests using it, and the eval framework had zero external consumers. The metric's behavior is unchanged.
- **`web_search` keyless chain: real browser UA, Baidu backend, parallel racing, recency filter, result dates**: the keyless path was weak on three axes — (1) the default User-Agent was an honest `moss-agent/0.1` bot UA that anti-bot endpoints challenge immediately; (2) the fallback chain was strictly serial, so a blocked primary burned its full timeout before the next engine was tried; (3) there was no way to ask for recent results, and no dates on results, so the model could not tell fresh from stale. Changes:
  - **UA**: default is now a current Chrome desktop UA (`Mozilla/5.0 (Windows NT 10.0; Win64; x64) … Chrome/124.0.0.0 Safari/537.36`); still overridable via `userAgent`.
  - **Baidu backend** (`baiduSearch`): keyless, parses `c-container` result blocks, unwraps the `baidu.com/link?url=` redirect to the real target URL, filters `result-op` ad blocks, extracts `c-color-gray` dates, and accepts a `gpc` time filter. CJK queries insert Baidu **after Bing, before DuckDuckGo** (Baidu's index is strongest for CJK; DuckDuckGo is unreachable from mainland China). Non-CJK queries skip Baidu (no advantage for English).
  - **Parallel racing** (`searchWithFallback` rewritten): backends start one by one with a 2.5 s grace window; if the current backend hasn't returned non-empty results in time, the next is launched concurrently; the first non-empty winner aborts the rest via a shared `AbortController`. The no-winner path awaits the **whole** chain (every launched promise) before falling through to empty/error — an earlier draft returned `[]` as soon as the first backend settled, which a fast-empty primary would short-circuit before later engines with real hits were waited for; caught by a regression test (`no-winner fallback waits for the whole chain`).
  - **`recency`** (`day`|`week`|`month`|`year`): new tool input + `WebSearchOptions.recency`; mapped to each backend's native keyless time filter — Bing `filters=exft:"N unit"`, DuckDuckGo `df=d/w/m/y` (HTML + Lite), Baidu `gpc=stf=<start>,<now>` (ms).

- **Context budget decisions now calibrated with real `prompt_tokens`**: after each successful LLM call, the agent loop stores the provider-reported `inputTokens` (= `prompt_tokens`, the model's real context measurement) as `lastReportedPromptTokens` in the mutable state. On the next turn, this value is used as a floor for character-based estimates — `max(estimate, lastReportedPromptTokens)` — preventing the planner from underestimating context usage when the character-to-token ratio drifts. The floor is reset to 0 after any compaction or overflow recovery (which fundamentally restructures the context), and at the start of each new user run.
- **Pre-existing build error fixed**: `cli-main.ts` referenced `parseLlmExtraBodyEnv()` which was never defined, causing `npm run build` to fail with `TS2304`. Replaced with an inline JSON parser for the `MOSS_LLM_EXTRA_BODY` environment variable.

### Changed

- **Default permission profile is now `autonomous`** (was `balanced`): a fresh install runs allowed tools without a per-call approval prompt. Writes/exec are still capped at the `workspace-write` ceiling, and `deniedTools` plus the dangerous-command floor still block risky calls — only the prompting is dropped. To get prompts back, pick `cautious`/`balanced` (`moss config set profile balanced`) or set `approvalPolicy prompt` / `MOSS_APPROVAL_POLICY=prompt`. The default safety ceiling is unchanged (`workspace-write`).
- **`formatHeadlessStreamEvent`** in `print.ts`: added `'llm_usage'` to the exhaustive switch so the headless formatter compiles cleanly after the `MossAgentEvent` union was extended.
- **`web_search` now prefers a real search API over keyless scraping**: the backend chain auto-selects a configured key-based provider (博查 Bocha → Brave → Exa) and only falls back to the keyless Bing / DuckDuckGo-Lite HTML scrapers as a degraded last resort. Microsoft retired the Bing Search API on 2025-08-11 and the keyless endpoints increasingly serve anti-bot/irrelevant pages, so when no real provider is configured Moss now says so honestly (empty/blocked results point the user at `BOCHA_API_KEY` / `BRAVE_API_KEY` / `EXA_API_KEY`) instead of passing off degraded results as real.
