### Added

- **IntentClassify (host routing)**: pure-heuristic `classifyUserIntent` for oneshot tool filters — `debug`/`coding`/`research`/`ops`/`plan_only`/`design`/`chat` — so web/plan/device tools route from intent without a second LLM call (Phase A of agent work-loop spec).

- **`web_search.allowed_domains` / `blocked_domains`**: post-filter result hosts by whitelist/blacklist (prefer over unsupported `site:` operators on keyless backends).
- **`fan_out_subagents` scope inference + retry checklist**: when `scope` is omitted, task text picks `explore` / `full` / `verify` / `plan` (so fix/implement slices no longer default to read-only explore). Failed children get a structured retry list for the parent.
- **FanOutNudge (mid-run)**: after a failed `fan_out_subagents` / `create_subagent` result, inject one soft system reminder to re-run FAILED angles or merge only SUCCESS evidence (pairs with end-of-turn FanOutMergeGate; max 1 fire per run).

### Fixed

- **Windows background-completion tests**: fixture scripts run with `workspaceDir` set to the temp fixture dir and bare `node <basename>.cjs` commands so cmd.exe no longer breaks on quoted relative paths (`Cannot find module ...\".moss-bg-...\"`).
- **Slow first-token latency on OpenAI-compatible gateways**: root causes addressed — (1) non-streaming complete path buffered the entire reply before any UI output; (2) unprobed 1M context derived `max_tokens` of 32k (doctor even claimed 128k), which many gateways schedule slowly; (3) pure-chat oneshot turns still paid for ~20 tool schemas + full skills index + git snapshot. Streaming + 8k max-output cap + pure-chat tool/skill/git elision.
- **Verification evidence gate no longer accepts arbitrary `exec`**: only verification-shaped commands (e.g. `npm test`, `npm run verify`, `tsc`) count; `exec echo hi` cannot unlock “done” after code edits.
- **Fresh green after last edit**: coding completion requires a green verification *result* that post-dates the last `edit_file`/`multi_edit`/`write_file`/`apply_patch` — earlier greens are stale; bare `exec_background` start without terminal result does not count.
- **Shell file mutations invalidate stale reads**: high-confidence `exec` rewrites (`sed -i`, redirects, `cp`/`mv`/`rm`/`tee`, …) clear prior-read credit and mark conversation `read_file` bodies stale for those paths — closes the thrash hole where shell bypassed surgical-edit discipline.
- **Full-file prior-read for surgical edits**: a partial `read_file` (`offset`/`limit`) no longer unlocks `edit_file` / `multi_edit` / `apply_patch` — require a full-file read (or a successful write/edit that re-stamps `full`) so paged reads cannot thrash on out-of-window `old_string`.
- **No “did not run tests but fixed” escape**: admitting tests were skipped only bypasses the coding verification gate when the reply is clearly incomplete / asking permission — not when it also claims done/fixed.
- **No done while background verification still runs**: finishing/success claims are blocked when a verification-shaped `exec_background` process (e.g. `npm test`) is still `running` — wait for completion evidence first.
- **`verify_fix` all-skipped / empty tests is not green**: when every step is skipped, or tests run but execute zero cases, status is `NO STEPS EXECUTED` / `NO TESTS EXECUTED` (is_error) instead of `ALL PASSED`, so completion gates cannot treat a no-op verify as success. Soft `exit 0` with empty stdout/stderr no longer counts as green either.
- **Fan-out merge honesty**: finishing with “all done” after `fan_out_subagents` / `create_subagent` results that include FAILED or empty children injects a correction to re-run failed angles or merge only successful evidence.
- **`apply_patch` stale-write guard**: update/delete of existing files now fails if mtime changed since the last full `read_file` (same discipline as `edit_file`), so concurrent editor/linter writes cannot be clobbered blindly.
- **Edit tool results embed change previews**: successful `edit_file` / `multi_edit` / `write_file` return a compact `--- change/write preview ---` with `-/+` lines so the transcript always shows what was written even when UI tool rows collapse.
- **Cross-platform clipboard attach (Ctrl+V)**: clipboard image/file paste no longer macOS-only — Linux uses `wl-paste`/`xclip`/`xsel`, Windows uses PowerShell clipboard APIs (Codex-style paste attach parity).
- **Empty test suite is not green**: `run_tests` with 0 executed tests reports `⚠️ NO TESTS EXECUTED` (and `is_error`) instead of `✅ ALL PASSED`, so completion gates cannot treat an empty/all-skipped suite as verification.
- **Success claims blocked on red verification / unresolved tool errors**: if the latest `run_tests`/`verify_fix` (or verification exec) failed, or a recent tool_result is an Error, claiming “all passed / fixed / done” (or quiet “done” after edits on red) injects one correction turn.
- **Blind-edit debug soft nudge**: under a fix/bug intent, if the model edits files without any investigation tool (`read_file` / `search_code` / reproduce `exec` / tests / …), inject one correction to locate or reproduce first (skips known one-line / admitted investigation).
- **Failure-driven completion gate reads `is_error` / `outcome`**: tool_results that flag `is_error: true` or `outcome: error|blocked|denied` count as failures even when the body does not start with `Error:` — closes a gap where failed `exec`/denied tools could be greenwashed.
- **Surgical-edit thrash break** (Claude FileEdit discipline): `old_string not found` errors now require `read_file` before retry; after 3 failed `edit_file`/`multi_edit` attempts on the same path in one turn (even with different `old_string`), the tool-loop guard short-circuits with a re-read instruction so the model cannot thrash stale patches.
- **`apply_patch` read-before-update**: updating or deleting an existing file via `apply_patch` now requires a prior `read_file` on that path (same as `edit_file` / `multi_edit`); failed update hunks tell the model to re-read and rebuild the patch instead of resubmitting the same body.
- **String-encoded tool failures set `is_error`**: tools that return `Error:…`, `Command failed`, `exit_code: N` (N≠0), `Patch rejected`, harness `Test Results: ❌` / `Verify Fix: ❌`, **or `code_diagnostics` `Result: FAIL`**, without throwing are now flagged as errors in the agent loop — so failure-driven completion gates, consecutive-error steering, and tool-loop failure counters actually see non-zero `exec` / red tests / soft edit failures (Claude/Codex discipline). Prefix matching is start-of-result only so a green test log that mentions `Error:` mid-body is not false-positive failed.
- **`apply_patch` thrash break**: repeated failed patches on the same file path short-circuit like edit_file (per-path), forcing re-read instead of resubmitting the same patch body.
- **`write_file` requires prior read on existing files**: overwriting a path that already exists now needs a prior `read_file` (create-new still free) so full rewrites cannot bypass surgical-edit thrash guards (Claude FileWrite discipline).
- **`move_file` overwrite requires prior read of destination**: `overwrite=true` on an existing destination needs `read_file` first so unread content is not destroyed.
- **Failed surgical edit invalidates prior-read credit**: after `edit_file` / `multi_edit` / `apply_patch` miss or reject on a path, Moss drops that path's read stamp so the next edit must `read_file` again — stops thrashing a stale in-memory snapshot before the path-level loop guard trips.
- **Multi-path edit thrash accounting**: `multi_edit` and `apply_patch` thrash counters now include **every** touched path (not only the first), so thrashing a later file in a batch cannot hide behind a clean leading path.

- **`exec` tool detects and suppresses binary output (e.g. `cat /bin/ls`)** — `runProcess` captures stdout as UTF-8, so binary commands produced MB of U+FFFD replacement chars + control chars that flooded the model's context (up to the 10MB maxBuffer). The exec tool now runs `looksBinary()` on stdout: if >10% of characters are non-printable (replacement chars, null bytes, or control chars other than `\n`/`\t`/`\r`), it returns a safe summary (`(binary output, N chars — suppressed...; use hexdump or xxd to inspect)`) instead of the raw garbage. Plain text with tabs/newlines and text with a low ratio of bad bytes are NOT false-positive'd. Verified by a new `exec-binary-output.spec.mjs`: real `/bin/ls` as UTF-8 is detected; synthetic binary (50% replacement/null/control chars) is detected; plain text, allowed whitespace, and large text with 1% replacement chars are not.
- **HTTP 500 is now retryable (was non-retryable 'unknown' — caused immediate failure on transient server errors).** `matchServiceUnavailable` matched 502/503 but not 500, so an Internal Server Error fell through to the default `'unknown'` category with `retryable: false` — the user saw an immediate failure instead of a retry on a possibly-transient 500 (gateway hiccup, temporary overload). 500 is now in the retryable 5xx set, and the message pattern includes "internal server error" for cases where the HTTP status isn't available. - **HTTP 529 (Anthropic overloaded) is now retryable in the write-through path.** After b206429 added 529 to `classifyProviderError`, the write-through `createProviderErrorResponse` (which sets `MossError.recoverable`) was missed — runtime retries still worked (they use the classifier) but any downstream that read `MossError.recoverable` directly got `false` for 529. 529 is now also in the write-through retryable set, so the two paths agree.

Verified by new `cli-security.spec.mjs` cases.

- **Logger child now respects the configured level dynamically (module-level `log.info` was leaking despite the default `info`→`warn` fix).** The earlier `resolveCliLogLevel` default→`'warn'` fix looked correct but didn't actually suppress `log.info` for module-level loggers. - **Foreground sub-agent `timeoutMs` was silently ignored**: `toolCtx.spawnSubagent` (the foreground path used by `create_subagent` without `background: true`) invoked `subAgentRunner` directly, bypassing the orchestrator's `runSingleChild` — which is the only place timeout enforcement existed for fan-out. So a foreground sub-agent whose model hung or looped would keep burning tokens until `maxTurns` or a parent abort, ignoring the `timeoutMs` the caller passed. `spawnSubagent` now builds its own `AbortController` that aborts on `timeoutMs` (default 120 s) **or** when the parent signal aborts, passes `controller.signal` to the runner, and clears the timer in a `finally`. The runner already converts an aborted signal into a failed `SubAgentResult`, so the parent receives a clean timeout failure instead of an unbounded wait. (Mirrors `runSingleChild`'s proven timeout structure; a dedicated subagent-timeout integration test is a follow-up — it needs a subagent harness that doesn't exist yet.)
- **Parallel tool groups bypassed the host approval hook**: when a turn produced a parallel-safe group of tool calls (readonly tools executed concurrently via `Promise.allSettled`), `executeOneToolCall` was called with `checkToolApproval: undefined`, so the host's approval callback was never invoked for those calls — no `tool_approval_request`/`tool_approval_resolved` events, no audit trail, no deny path — while the same tools executed serially went through the hook. The parallel branch now passes `checkToolApproval` through, matching the serial path. Parallelism is preserved because parallel groups only contain readonly tools (filtered to readonly above), whose approval typically resolves to `null` (no prompt); the hook now runs per-call inside each concurrent `executeOneToolCall` rather than being skipped.
- **`SessionManager` cache returned stale context after truncation/compaction**: `truncateTrailingAssistant`, `truncateForRegenerate`, and `appendCompaction` mutated the session entry tree but never cleared `state.cachedContext`. The next `getContextMessages` call returned the *pre*-mutation message list (the cache only checks `cachedContext !== null`, with no version check), so a truncated or compacted session could keep feeding stale context to the model until the cache was evicted by an unrelated write. All three mutation paths now set `state.cachedContext = null`, matching the existing append path's invalidation. (`SessionManager` is a public API not exercised by the CLI, but any host embedding moss that drives truncation/regenerate/compaction through it was affected.)

### Fixed

- **Context-usage % now uses the model's real context window**: the usage-bar denominator was hard-coded to 200k for every model, so a 1M-context model like `glm-5.2` reported ~5× inflated usage (e.g. "50% context used" when only ~10% was actually consumed) and triggered auto-compaction roughly 5× too early, throwing away usable context. Moss now defaults the window to **1M** — matching the gateway / long-context models it is normally pointed at (deepseek, qwen, glm-5) — and carves out the built-in providers with smaller real ceilings (OpenAI `gpt*` → 128k, Anthropic `claude*` → 200k) so they don't over-shoot and hit "input exceeds maximum". An explicit `agent.contextTokens` / `MOSS_CONTEXT_TOKENS` still takes precedence, and the resolved source is reported as `model` in `moss doctor`/setup output.
- **Context escalation path continuity**: the four-tier escalation ladder (warning → proactive → hard cap → overflow recovery) had multiple dead zones and threshold inversions that prevented accurate context-usage feedback and proactive protection. Fixed: (1) the hard cap is now dynamic (90% of effective context window) instead of a fixed 125K, so it always sits above the proactive threshold — previously on 200K models the hard cap fired *before* the proactive threshold, bypassing window economics entirely; (2) the redundant `shouldTriggerCompaction` gate was removed from the proactive compaction path — it was always stricter than `shouldProactiveCompactByWindowEconomics`, making the dynamic buffer dead code and delaying compaction by ~15K tokens; (3) the warning band now scales to 10% of the effective window on small models (was a fixed 20K, which collapsed the warning threshold to 0 on 32K gateways, triggering warning-level actions on every turn); (4) the steering `contextUsageRatio` now includes the system prompt and uses the same `estimatePromptUnitsForContextWindow` function as the planner, so the 0.75 context-pressure steering rule is directly comparable to the planner's thresholds — previously it excluded the system prompt, underestimating actual usage.
- **Proactive compaction restored after overflow recovery**: after a successful overflow recovery (cheap/LLM/truncate), the `proactiveCompactionAttempted` and `promptPruneCompactionAttempted` one-shot flags are now reset, allowing proactive compaction to fire again if the context regrows — previously the flags stayed true until the next user message, degrading protection to reactive-only (overflow errors).
- **Stale-read invalidation during tool follow-up rounds**: `invalidate_stale_reads` now runs during tool follow-up rounds (the planner's `tool_followup_round` branch, previously dead code because the execution layer short-circuited all context management). Stale reads no longer accumulate during tool-dense sessions. The last `tool_result` is never touched — `invalidateStaleReadToolResults` only replaces old reads superseded by a later write.
- **Context-overflow error message accuracy**: the `context_length_exceeded` error surface now says "对话上下文已超出模型限制" instead of the misleading "本轮模型流式连接在长上下文处理后中断" which sounded like a network/streaming issue.
- **Model context window resolution expanded and made accurate**: `resolveModelContextWindow` previously matched only `gpt` (128K) and `claude` (200K), defaulting everything else — including `glm`, `deepseek`, `qwen`, `llama`, `mistral` — to 1M. This was wrong for models with smaller real ceilings (e.g. `deepseek` native 64K, `qwen` 32K, `gemma` 8K), causing overshoot and `context_length_exceeded` errors. The matcher now covers 12+ model families with their real native context windows. The combined resolver (`resolveContextTokensForModel`) tries: explicit override → API query → name matching → 1M fallback. The resolved source is reported in the TUI transcript (e.g. "Context window: 32,000 tokens (via ollama-api)").
- **`/model` switch now recalculates context window**: when a user switches models via `/model`, the session's `contextTokens` is now re-resolved from the new model's real context window (unless the user explicitly overrode it via CLI flag or `MOSS_CONTEXT_TOKENS`). Previously, switching from a 200K model to a 32K model left the session still using 200K, causing overshoot and `context_length_exceeded` errors on the new model.
- **Context usage bar now shows real per-call token counts (not cumulative sum)**: the `llm_usage` event forwarded by `MossAgentLoopEventAdapter` was accumulating `inputTokens` and `outputTokens` across all turns, so the TUI displayed `Σ(all_turns_input) + Σ(all_turns_output)` — double-counting the same context multiple times and inflating the displayed usage.
